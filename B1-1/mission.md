# 미션: LLM 프롬프트 엔지니어링과 업무 자동화

## 1. 미션 소개

> "ChatGPT한테 물어봤는데, 생각보다 별로던데요?"

한 번쯤 이런 허탈함을 느껴본 적이 있을 겁니다. 분명 세상을 바꿀 혁명이라고 하는데, 막상 내 업무를 맡기면 엉뚱한 대답만 늘어놓거나 겉도는 말만 반복하는 AI. 그런데 옆자리 동료는 같은 AI로 보고서 초안부터 데이터 요약까지 뚝딱 해치웁니다. 도대체 뭐가 다른 걸까요?

답은 의외로 간단합니다. **질문을 어떻게 설계했느냐**의 차이입니다.

같은 모델이라도 프롬프트 한 줄이 달라지면 결과물의 수준은 완전히 바뀝니다. '그냥 물어보는 것'과 '제대로 시키는 것' 사이의 간극을 직접 체감하는 것이 이번 미션의 출발점입니다.

이번 미션에서는 대규모 언어 모델(LLM)의 작동 원리를 이해하고, 프롬프트 엔지니어링을 통해 원하는 텍스트 결과물을 정교하게 제어하는 기술을 익힙니다.

먼저 3종 이상의 LLM을 동일한 업무 과업에 투입해 성능을 비교하고, "느낌"이 아닌 평가 축과 근거로 최적의 모델을 선정하는 방법을 학습합니다. 이어서 특정 페르소나를 가진 AI 챗봇의 시스템 프롬프트를 직접 설계하고, Few-shot 예시와 단계적 추론 유도 기법을 적용해 프롬프트를 버전별로 개선해 나갑니다.

단순한 질문-답변을 넘어 10턴 이상의 대화에서 문맥을 유지하며 논리적으로 대화를 이끌어가는 텍스트 생성 파이프라인을 구축하고, 환각(Hallucination)을 체계적으로 검증하는 과정까지 경험합니다.

이 과정을 마치면, 여러분은 AI를 단순한 검색 대용이 아니라 업무 생산성을 끌어올리는 핵심 파트너로 다룰 수 있게 됩니다. "프롬프트를 잘 쓰는 사람"과 "그냥 물어보는 사람" 사이의 격차는 생각보다 큽니다.

이 미션에서 쌓은 프롬프트 설계, 검증, 개선 역량은 향후 멀티모달 콘텐츠 제작과 AI 서비스 개발의 튼튼한 밑거름이 될 것입니다.

## 2. 최종 결과물

다음 3가지 산출물을 포함한 **업무 자동화 프롬프트 패키지 1개**를 완성합니다.

### 2.1 LLM 모델 비교·선정 보고서

- 문서 1개를 제출합니다.
- 동일한 업무 과업 프롬프트를 3종 이상의 모델에 입력합니다.
- 테스트 질문 또는 테스트 케이스를 포함합니다.
- 모델별 결과 비교표와 최종 선정 결론을 근거와 함께 정리합니다.

### 2.2 시스템 설계 문서

- 문서 1개를 제출합니다.
- 다음 항목을 포함합니다.
  - 타겟 사용자
  - 업무 문제
  - 페르소나
  - 시스템 프롬프트와 유저 프롬프트
  - Few-shot 예시
  - 검증 전략
  - 프롬프트 버전 개선 이력(v1 -> v2)
  - 최종 프롬프트 전문

### 2.3 실행 로그

- 대화 로그 1개를 제출합니다.
- 선택한 업무 과업 시나리오로 10턴 이상 실제 대화를 수행한 전문을 남깁니다.
- 문제 발생 지점과 수정 결과 요약을 포함합니다.
  - 환각
  - 문맥 끊김
  - 형식 미준수
  - 조건 누락

## 3. 과제 목표

이 과제를 마친 후, 학습자는 아래 내용을 스스로 설명할 수 있어야 합니다.

- LLM이 **확률적 생성** 기반으로 동작하며, 왜 환각(Hallucination)이 발생하는지 설명할 수 있다.
- Zero-shot, Few-shot, 단계적 추론 유도(Reasoning Prompt) 기법의 차이를 구분하고, 업무 과업에 맞게 적용할 수 있다.
- 3종 이상의 LLM을 비교할 때, "느낌"이 아니라 평가 축과 근거를 통해 선택 이유를 설명할 수 있다.
- 페르소나와 시스템 프롬프트가 결과 품질에 미치는 영향을 설명할 수 있다.
  - 일관성
  - 안전성
  - 형식 준수
- 생성 결과를 테스트로 검증하고, 특히 사실 오류를 확인하며, 프롬프트를 반복 개선하는 과정을 재현 가능하게 설명할 수 있다.

## 4. 기능 요구 사항

다음 요구사항을 모두 만족해야 합니다.

### 4.1 모델 비교 및 선정

서로 다른 3개 이상의 LLM을 선정해 동일한 업무 과업을 수행시킵니다.

예시 모델:

- GPT-4o
- Claude 3.5 Sonnet
- Gemini 1.5 Pro
- 또는 동급/유사 목적의 최신 모델

모델 비교 보고서에는 아래 항목을 반드시 포함합니다.

- 비교 대상 모델명
- 사용 환경
  - 웹
  - 앱
  - API
- 평가 축 최소 4개
- 모델별 점수(1~5)
- 모델별 평가 근거
- 최종 선정 결론
  - "왜 이 모델이 업무 과업에 최적"인지 3줄 이상 근거로 설명

### 4.2 업무 자동화 과업 선택 및 문제 정의

아래 예시 중 1개 이상을 선택하거나, 본인 업무에 준하는 과업을 정의합니다.

- 메일 초안 작성
  - 요청
  - 상황
  - 톤 지정
- 회의록 요약
  - 결정사항
  - Action Items 추출
- 보고서 개요 생성
  - 목차
  - 핵심 메시지
  - 리스크
- 요구사항 정리
  - 사용자 스토리
  - 수용 기준

선택한 과업에 대해 다음을 문서에 명시합니다.

- 타겟 사용자: 누가 쓰는가?
- 입력 데이터 형태: 어떤 정보를 받는가?
- 출력 규격: 어떤 형식으로 내야 하는가?
- 입력 템플릿 1개 이상
  - 학습자가 재사용 가능한 형태로 작성

입력 템플릿 예시:

```text
[목적]
[대상]
[핵심 포인트]
[톤]
[금지어]
[필수 포함 항목]
```

### 4.3 페르소나 정의 및 시스템 프롬프트 설계

페르소나는 구체적으로 정의합니다.

- 이름
- 역할 또는 직무
- 전문 분야
- 말투
- 금지 사항
- 우선순위
  - 정확성
  - 친절함
  - 간결성
  - 안전성

시스템 프롬프트에는 최소 아래 요소가 포함되어야 합니다.

- 역할(페르소나)과 목표(업무 과업)
- 출력 형식 규칙
  - 제목
  - 불릿
  - 표
  - 표현 톤
- 안전장치
  - 모르면 모른다고 말하기
  - 확인 질문하기
- 사실, 정책, 수치가 포함될 때의 처리 규칙
  - 근거 제시
  - 확인 필요 표기

### 4.4 Few-shot 예시

동일 과업에 대해 **좋은 입력 -> 좋은 출력** 예시를 최소 3개 제공합니다.

- 예시 3개 중 1개는 반드시 **모호한 입력** 케이스로 구성합니다.
- 모호한 입력 케이스에서는 AI가 되물어야 하는 지점을 보여줍니다.

### 4.5 단계적 추론 유도 적용 및 전/후 비교

같은 과업 입력에 대해 다음 두 버전을 비교합니다.

- v1: 일반 지시
  - 간단 프롬프트
- v2: 단계적 접근을 유도하는 프롬프트
  - 먼저 요구사항 정리
  - 누락 질문
  - 초안 작성

단, 최종 출력에는 불필요한 장문의 추론 과정이 그대로 노출되지 않도록 **최종 답변은 요약/근거 중심** 규칙을 함께 둡니다.

예시:

```text
내부적으로 단계적으로 검토하되,
최종 답변에는 핵심 근거 3개만 bullet로 제시한다.
```

### 4.6 환각(Hallucination) 검증

이 미션에서 환각은 다음으로 정의합니다.

> 사실, 수치, 정책, 계산처럼 정답 또는 검증 가능한 근거가 있어야 하는 질문에서 근거 없이 틀린 정보를 확신하는 답변

창의적 글쓰기(예: 소설, 카피)는 환각으로 보지 않습니다. 단, "허구"임을 명시하거나 세계관 규칙을 지켜야 합니다.

사실 기반 검증 질문을 5개 이상 준비하고, 각 질문에 대해 아래 내용을 함께 기록합니다.

- 기대 정답 또는 정답 판정 기준
- 허용 오차
  - 필요한 경우
- 참고 근거
  - 출처 링크를 붙일 수 있으면 좋으나 필수는 아님

합격(Pass) 기준은 둘 중 하나라도 충족하면 됩니다.

- 정답을 맞히고, 근거를 간단히 제시한다.
- 확인 가능한 방식으로 설명한다.
- 모르면 "모른다" 또는 "확인 필요"를 명시하고, 확인 절차를 제안한다.
  - 어디서
  - 무엇을
  - 어떻게 확인할지

실패(Fail) 기준은 하나라도 해당하면 실패입니다.

- 틀린 사실을 단정적으로 말한다.
- 근거 또는 불확실성 표기가 없다.
- 질문의 전제가 불명확한데도 확인 질문 없이 임의로 사실을 만들어 답한다.

### 4.7 10턴 이상 대화 로그 및 문맥 유지 검증

선택한 업무 과업 시나리오로 10턴 이상 대화를 수행하고 전문을 남깁니다.

아래 상황 중 1개 이상을 반드시 포함합니다.

- 중간에 조건 변경
  - 톤
  - 대상
  - 정책 변경
- 추가 정보가 뒤늦게 제공됨
  - 첨부 내용
  - 제약 조건

문맥 유지는 다음을 모두 만족하면 Pass로 판정합니다.

- 이전에 확정된 요구사항을 10턴 내내 일관되게 유지한다.
  - 톤
  - 대상
  - 금지어
- 조건 변경이 들어오면, 변경된 부분만 반영하고 나머지는 유지한다.

### 4.8 제출물 최소 목차

형식은 자유지만, 아래 항목은 필수입니다.

#### 모델 비교·선정 보고서

- 비교 목적
- 비교에 사용한 동일 입력
- 평가 축과 점수표
- 모델별 결과 요약
- 최종 선정 근거

#### 시스템 설계 문서

- 문제 정의
- 타겟 사용자
- 업무 과업 입력 템플릿
- 페르소나
- 시스템 프롬프트
- Few-shot
- 환각 검증 설계
- 개선 이력(v1 -> v2)

#### 실행 로그

- 시나리오 설명
- 10턴 이상 대화 전문
- 문제 지점과 개선 요약

## 6. 제약 사항

### 6.1 모델 및 환경 기록

재현성을 위해 최소 기록 항목을 제출물에 반드시 포함합니다.

- 모델명
- 요금제
  - 무료
  - 유료
- 사용 채널
  - 웹
  - 앱
  - API
- 사용 날짜
  - YYYY-MM-DD
- 주요 설정
  - 가능한 범위에서 temperature, top_p, max_tokens 등
- 무료 버전 사용 시 제한된 점 1줄

### 6.2 안전 및 윤리

- 폭력적 또는 선정적 콘텐츠 생성을 시도하지 않습니다.
- 개인정보를 프롬프트나 로그에 직접 포함하지 않습니다.
  - 실명
  - 전화번호
  - 주소
  - 계정정보
- 사실, 정책, 수치가 포함되는 답변은 **근거/확인 필요** 규칙을 반드시 따릅니다.

### 6.3 제출물 편집

- 대화 로그를 그대로 덤프하지 말고, 가독성을 위해 섹션, 번호, 요약을 추가해 정리합니다.
- 단, **원본 로그 전문**은 별도 파일로라도 남겨 재현 가능하게 합니다.

## 7. 결과 예시

아래는 정답이 아니라 참고 예시입니다. 실제 문구와 구성은 달라도 됩니다.

### 7.1 모델 비교 보고서 일부

비교 축 예시:

| 번호 | 평가 축 |
| --- | --- |
| 1 | 정확성(사실/계산) |
| 2 | 한국어 자연스러움 |
| 3 | 긴 문맥(10턴) 유지 |
| 4 | 형식 준수(템플릿 출력) |
| 5 | 속도/안정성 |
| 6 | 비용(요금제/토큰) |
| 7 | 도구 연동 적합성 |

결론 예시:

> "회의록 요약" 과업은 긴 문맥 유지와 형식 준수가 중요하므로, 해당 축 점수가 높은 모델을 채택한다.

### 7.2 업무 과업 입력 템플릿

```text
[업무 과업] 회의록 요약

[원문] 회의 메모/녹취 요약 텍스트

[원하는 결과] 결정사항 / Action Items / 리스크 / 후속 일정

[톤] 간결, 사내 공유용

[금지] 추측성 표현 금지, 인물 실명 대신 역할명 사용

[확인 질문 규칙] 정보가 부족하면 최대 3개까지 질문 후 요약 시작
```

### 7.3 페르소나 및 시스템 프롬프트 요약

페르소나:

> 프로젝트 매니저 출신 업무 자동화 코치

원칙:

1. 사실, 수치, 정책은 확인 가능해야 한다.
2. 정보가 부족하면 질문한다.
3. 최종 출력은 템플릿을 준수한다.

### 7.4 Few-shot 예시 1개

입력 예시:

```text
회의 메모가 너무 길어. 결정사항과 할 일만 뽑아줘.
대신 확실한 내용만.
```

출력 예시:

```text
- 결정사항: ...
- Action Items: 담당 / 기한 / 작업 ...
- 확인 필요: ... (근거 부족 항목)
```

### 7.5 단계적 추론 유도 프롬프트 전/후

v1(간단):

```text
아래 회의 내용을 요약해줘.
```

v2(개선):

```text
1. 먼저 목표 출력 항목(결정 / 할 일 / 리스크)을 선언한다.
2. 정보가 부족하면 최대 3개 확인 질문을 한다.
3. 마지막에 템플릿으로 출력한다.
4. 최종 답변에는 핵심 근거 3개만 짧게 덧붙인다.
```

### 7.6 환각 검증 기록

질문:

```text
(업무 규정) 출장비 정산 규정의 예외 조건이 뭐야?
```

Pass 예시:

```text
규정 문서가 없으면 확답할 수 없습니다.
사내 위키 또는 규정 PDF의 '예외' 섹션을 확인해야 합니다.
확인 후 요약 제공이 가능합니다.
```

Fail 예시:

```text
예외는 무조건 ... 입니다.
```

실패 이유:

- 근거 없이 단정적으로 답변함

### 7.7 10턴 대화 로그

```text
1. 사용자: 회의록 원문 제공
2. AI: 확인 질문 2개(누락 정보)
3. 사용자: 추가 정보 제공
4. AI: 템플릿 요약 출력
...
9. 사용자: "톤을 더 단호하게, 책임자를 역할명으로 바꿔줘"
10. AI: 변경 반영 + 기존 결정사항 유지
```
