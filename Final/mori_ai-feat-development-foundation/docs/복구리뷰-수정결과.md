## RED와 원인

- missing/null caption 및 nonready/wrong-owner asset은 running 또는 unknown에 남았다.

checksum은 파일 무결성만 확인하며 stage 결과의 유효성을 보장하지 않는 것이 원인이다. 기존 run_once는 settlement False를 무시했고 recover는 같은 invalid 결과에 계속 lease/fence를 부여했다.

## 정책과 변경

`backend/generation/repository.py`에 DB 필드 대입 전 결과 검증과 invalid 실패 처리를 추가했다. caption은 문자열이며 strip 후 비어 있지 않아야 한다. asset은 UUID 파싱·존재·owner/album/page 일치·ready·deleted_at 없음 조건을 확인한다. 존재하지 않는 UUID를 FK에 대입하지 않으며 원래 raw 결과는 attempt 경로의 checksum envelope에 그대로 남는다.

invalid 결과는 task=failed, lease=null, task/attempt error_code=`CAPTION_INVALID` 또는 `MEDIA_SAVE_FAILED`, album/run=action_required로 수렴한다. `safe_to_retry=false`를 명시한다. 이 수정에서는 invalid 참조를 로컬에서 안전하게 수선할 수 있다는 증거가 없으므로 로컬 task도 보수적으로 재개 불가로 둔다. 실제 파일 재저장 등 로컬 수선 정책은 후속 adapter 연동에서 별도로 정의해야 한다. 유료 AI 재호출이나 invalid 원본 응답 삭제는 추가하지 않았다.

`backend/worker/runner.py`의 수신·recover가 같은 검증을 사용한다. settlement False는 다시 album/run/task lock과 active fence를 확인하여 현재 유효 claim의 invalid 결과만 실패 처리한다. stale/deleted/expired claim은 상태를 덮어쓰지 않는다. 수신 뒤 asset이 삭제되는 경우도 명시적 실패로 끝난다. 삭제된 album/page의 결과 연결 차단과 cleanup_asset 멱등 예약을 유지하며 잘못된 UUID 자체에는 정리할 유효 asset이 없다. 같은 attempt의 늦은 응답은 원래 결과 확인을 위해 보존한다.

DB received fallback은 caption뿐 아니라 보존 asset 참조도 읽는다. malformed UUID/FK 오류를 검증 단계에서 처리하므로 다른 정상 task의 복구와 background maintenance가 계속된다. 임의 DB 장애를 삼키는 포괄적 exception 처리는 추가하지 않았다.
