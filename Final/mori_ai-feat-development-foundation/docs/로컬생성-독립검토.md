## Important I1 — 원래 unknown 결과를 회수해도 미발송 queued AI 단계가 남으면 재개할 수 없다

**위치:** `backend/worker/runner.py:252-282` (원래 결과 회수·settlement), `backend/generation/completion.py:23-25` (미완료면 상태 복원 없이 반환). 차단 경로는 `backend/generation/repository.py:33`, `backend/generation/resume_policy.py:18-20`, `backend/generation/views.py:46-52`다.

**구체 trigger:** image 또는 caption이 unknown이 될 때 다른 페이지/단계의 AI task가 아직 queued/retry_wait이며, 이후 원래 응답을 정상 회수한다. 단일 worker에서도 UUID task 실행 순서상 먼저 실행한 image의 응답 유실만으로 가능하다. 회수한 task는 succeeded가 되지만 run은 action_required를 유지한다. 로컬 optimize는 끝낼 수 있어도 아직 발송하지 않은 caption/image는 action_required의 claim 정책에 막힌다. eligible_resume_tasks는 failed만 반환하므로 queued 작업을 사용자가 이어서 실행할 수도 없다.

**사용자 영향:** 불확실한 결과와 실패가 모두 없어졌는데 진행 화면은 계속 준비 중이고 재개 버튼도 없다. 새로고침·worker 재시작·scanner로도 해결되지 않으며 사진첩을 삭제해야 사용자별 미완료 run 1개 제한이 풀린다. 보존한 정상 결과가 있어도 작업을 버리게 되는 주요 복구 결함이다. unknown의 같은 요청을 재호출하는 것이 아니라, 아직 한 번도 발송하지 않은 별도 단계의 최초 실행이 막히는 문제다.

**재현 / 추론 구분:** 실제 독립 PostgreSQL 17.11 + 실제 FakeExecutor/WebP 파일로 재현했다. 이 probe의 unknown 전이는 DB에서 장애 경계 상태를 주입했으며 OS kill 자체를 재실행한 것은 아니다. 기존 강제 kill 검사는 별도로 대상 회귀에 포함됐다. probe는 네트워크 없는 전용 tmp DB, MORI_WORKFLOW_TEST=1 및 DB 이름 guard, source read-only mount, container /tmp, 독립 project/network/volume/EXIT cleanup을 사용했다.

재현 순서:

1. 기존 `pipeline(..., count=2)`로 portrait/landscape 두 페이지와 실제 normalized 파일·생성 run을 만든다.
2. landscape image만 먼저 claim되도록 나머지 queued task의 next_retry_at을 잠시 미래로 둔다.
3. 기존 claim_task → Runner.prepare → _mark_sent → FakeExecutor.execute를 호출하여 같은 원래 attempt의 transform_output 및 durable envelope를 실제로 저장한다.
4. task를 unknown, run/album을 action_required로 두고 나머지 next_retry_at을 해제한다.
5. Runner.recover() → 기존 drain(runner) → 실제 GET generation을 호출한다.

실제 결과:

```json
{"recovered":1,"run_status":"action_required","unknown":0,"failed":0,"pending":2,"can_resume":false,"poll_after_ms":null}
```

두 페이지 모두 image_transform/optimize=succeeded이고 caption=queued다. portrait image는 passthrough다. 원래 image 결과가 회수됐는데도 caption은 최초 발송조차 되지 않는다. probe 종료 후 전용 container/network/volume 정리를 확인했다.

**최소 수정 방향:** 원래 결과 회수 이후 더 이상 unknown이 없을 때, 보류된 미발송 AI task를 사용자의 명시 재개로 진행할 수 있게 상태·eligible policy를 함께 정리해야 한다. 현재 공개 resume의 failed-only 의미를 유지하려면 마지막 unknown 해소 시 잠금 transaction 안에서 보류된 안전한 미발송 task를 failed + safe_to_retry로 분류해 기존 resume 경로에 포함하는 방식을 고려할 수 있다. 이미 성공한 task·원래 unknown attempt는 재발송하지 않으며, 아직 unknown이 남으면 새 AI 발송 차단을 유지해야 한다. 자동 처리 재개를 택한다면 action_required의 명시 재개 계약과의 관계를 먼저 확인한다. 순수 UI 버튼 표시 변경으로는 서버 claim 차단을 해결하지 못한다.

**필요 회귀:** 다른 task를 queued 그대로 둔 image/caption unknown→원래 결과 회수, retry_wait 보류, 복수 unknown 중 하나만 회수, 마지막 unknown 회수, 삭제 경합을 검사한다. 원래 attempt 호출 수 불변·미발송 단계 최초 1회·review_ready까지 완료를 확인한다. 기존 `test_generation_pipeline.py:142-143`은 다른 queued task를 모두 failed/safe_to_retry로 바꿔 놓고 `:178`에서 resume하므로 이 경로를 잡지 못한다.
