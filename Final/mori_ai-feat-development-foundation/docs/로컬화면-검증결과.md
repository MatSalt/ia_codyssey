# 로컬 화면 구현·검증 결과

## 인터페이스 확인과 구현 판단

Task1 실제 `/api/dev/config` 응답은 `data.dev_auth_enabled`다. 문구상의 enabled가 아니라 실제 boolean이 true일 때만 alpha/beta 개발 버튼을 표시한다. 로그인은 명확하게 ‘개발용 가짜 로그인’으로 안내한다.

예약·초안 생성은 동일 의도의 요청 body와 Idempotency-Key를 메모리에 유지한다. 네트워크 오류·timeout에 재시도해도 새 키를 생성하지 않는다. 예약의 명확한 4xx 거부(401 제외)는 파일을 유지하고 다음 수동 요청에서 최신 상세와 새 의도를 구성한다. 예약이 성공한 뒤에는 동일 reservation으로 재시도한다. 실패·만료 페이지는 확인 후 삭제하고 다시 첨부한다.

세션 만료 시 선택 파일·생성 키·예약 의도는 사용자 ID별 메모리에 보존한다. 로그아웃 시 query cache와 해당 메모리를 지운다. reload 후 로컬 파일은 복원하지 않는다. Blob URL을 생성하지 않아 Blob URL 잔류는 없다. API가 주는 asset ID를 기준으로 미디어 접근 URL을 연결하고 만료 시 재발급한다.

상세 조회의 upload_status를 visible 탭에서 1.8초 주기로 조회한다. hidden 탭에서는 주기 조회를 멈추고 복귀 시 최신 상세를 조회한다. 업로드 전·complete 후·수동 순서와 삭제 직전 최신 상세를 조회한다. 수동 순서는 모든 active page ID와 최신 album version을 보낸다. Query 조회와 파일 전송은 unmount 시 AbortSignal로 취소한다.

## 실행 검증

`docker build --target frontend -t mori-ai-task4-frontend-check .`로 기존 Dockerfile frontend target을 빌드했다. Node 24 컨테이너의 기존 lock 기반 npm ci 및 `npm run build` 안의 `tsc --noEmit`, Vite production build가 통과했다. 독립 검증 태그만 만들었고 공유 runtime 태그·lock·설정은 변경하지 않았다. 호스트 dependency 설치와 Git 작업을 하지 않았다.

이 결과는 **build only**다. backend 전체 성공, 실제 OAuth·R2·AI 성공, 브라우저 동작 성공을 뜻하지 않는다. Task3 업로드 경계가 병렬 구현 중이며 총괄이 관리하는 통합 URL이 제공되지 않아 실제 browser·DB 회귀·모바일 실기기 검증은 미실행이다. 신규 브라우저 test dependency는 추가하지 않았다.

## 총괄에게 넘기는 통합 검증 흐름

1. 개발 로그인 비활성 환경에서 alpha/beta 버튼이 없는지 확인한다. 활성 로컬 환경에서 alpha 로그인 → 동의 거절·logout → 재로그인 → 최신 notice/policy 동의 → 빈 책장을 확인한다.
2. 새 사진첩을 만들고 서버 UUID의 `/edit`로 이동한다. 응답 유실 후 같은 생성 요청 재시도로 한 초안에 수렴하는지 확인한다.
3. JPEG/PNG/WebP·8bit HEIC(빈 MIME 포함)를 복수 선택한다. 예약→PUT→complete→validating→ready 및 서버 WebP 썸네일 전환을 확인한다. HDR 실패는 전체 HEIC 성공으로 보고하지 않는다.
4. 네트워크 차단·timeout·예약 응답 유실·PUT/complete 응답 유실을 만들고 같은 키·의도로 재시도되는지 확인한다. 401 재로그인 후 같은 사용자 입력 복원, 409 최신값 안내, 413/422 입력 유지도 확인한다.
5. batch 완료 역전 중 임시 순서 안내·수동 앞뒤 이동·전체 ID/version·manual 유지와 실패 페이지 삭제/재첨부를 확인한다.
6. hidden 탭 polling 중지/복귀 refetch, reload 후 로컬 파일 소실 안내, 썸네일 URL 만료 재발급, 사진첩 삭제 확인을 확인한다.
7. logout 후 beta 로그인에서 alpha 목록·이미지·선택 파일·query cache가 나타나지 않는지 확인한다. 키보드 focus·버튼 라벨·모바일 폭·색 대비를 실제 browser에서 확인한다.

## 총괄 합류 중 수정

PUT required_headers의 고정 세션 토큰은 재로그인 후 유효하지 않으므로 same-origin /api PUT에 최신 메모리 CSRF를 별도 전달하도록 수정했다. 외부 저장소 origin으로 토큰을 보내지 않는 것과 logout 후 제거를 포함한 Node24 회귀 3개가 통과했다. 최초 amd64 지정 실행은 해당 임시 frontend 이미지가 arm64라 테스트 시작 전 실패했으며 RED에서 제외했다. 실제 Node 회귀는 native arm64에서 수행했고 최종 Dockerfile frontend stage에도 포함해 linux/amd64 통합 빌드에서 재실행한다.

실제 Orca 브라우저 RED: 동의 거절→재로그인→동의→책장→새 사진첩→로그아웃 뒤 /me는401이지만 화면은 ‘사진첩을 준비하고 있어요…’에 머물렀다. session query 관찰자를 유지하면서 private query 취소·제거 후 session=null로 갱신하는 resetSession을 추출해 수정했다. 관찰자·다른 사용자 데이터 제거·pending query 취소의 Node 회귀 3개가 통과했다. 초기 401 처리에서 public dev-config 요청을 취소하지 않는 회귀도 포함한다.

## 총괄 실제 합류 검증 (2026-10-16)

Orca 브라우저의 전용 로컬 환경에서 동의 거절→재로그인→동의→초안 생성, JPEG·투명 PNG·8bit HEIC 세 장 업로드→모두 준비 완료와 서버 썸네일을 확인했다. 로그아웃 뒤 개발 로그인 화면 정상 복귀를 재확인했다. beta 로그인·동의 뒤 alpha 사진첩 상세는 찾을 수 없음으로 차단되고 beta 책장은 비어 있다. 실제 OAuth·모바일 실기기·HDR 품질 검증은 미실행이다.

최종 linux/amd64 재현 설치는 backend 103 passed/DB 110 skipped와 frontend Node 회귀 6개·tsc/Vite를 통과했다. 별도 실제 PostgreSQL 전체는 213 passed(52.69초), 두 환경 DB/media 격리 및 worker SIGTERM 종료 0도 통과했다. 독립 검토는 후속 진행한다.

추가 브라우저 확인: 수동 순서 변경 뒤 reload·재로그인에도 manual 순서와 세 미리보기가 유지됐다. 16bit PNG는 검증 실패로 표시됐고 실패 페이지 삭제 후 다시 3장으로 수렴했다(확인 dialog 응답은 테스트에서 승인으로 대체). PUT가 서버에서 성공한 직후 클라이언트에 응답 유실을 한 번 주입하면 같은 업로드 재시도가 표시되며, 재시도 후 중복 페이지 없이 4장 모두 ready가 됐다.

리뷰 수정 합류: linux/amd64 최종 재현 빌드와 Node 11개(기존6+선택5)가 통과했다. 수정된 runtime에서 application/octet-stream인 synthetic .HEIC File 객체를 선택했을 때 오류 없이 선택 목록과 업로드 버튼으로 연결됨을 실제 Orca 브라우저에서 확인했다. 이 검사는 선택 조건의 확인이며 synthetic bytes를 HEIC로 디코딩 성공했다고 주장하지 않는다. 최종 실제 DB 전체는 추가 복구 보호 회귀를 포함해 224 passed(53.23초)다.
