## 실제 저장소 확인

`MORI_STORAGE_VERIFY_IMAGE=mori-ai:r2-tests make verify-storage` 성공. 고유 `mori-ai-storage-check/<UUID>/` 아래 합성 PNG/JPEG/8비트 HEIF만 사용했다. 세 형식의 presigned PUT, remote HEAD/원본 SHA256, 조건부 중복 PUT 412, signed HEAD/GET, unsigned S3 endpoint 거부, object 삭제 확인 모두 통과했다. remote attempt envelope 쓰기/회수와 생성 객체 정리도 통과했다.

CORS는 APP_ORIGIN=http://127.0.0.1:8000에서 PUT preflight의 Content-Type/If-None-Match, GET ETag 노출, 미허용 origin 거부를 실제 확인했다. [콘솔 JSON](storage/r2-cors.local.json)을 사용한다. unsigned S3 거부는 public r2.dev/custom domain 설정 전체 감사와 다르다.

최초 2초 GET URL 검증은 8초 대기 내 만료되지 않았다. 진단에서 Docker의 UTC 시각이 R2 HTTP Date보다 약 13초 앞섰고 서명 TTL은 실제 2였다. 상한 45초의 bounded polling으로 서버 Date가 서명 시각+TTL을 지난 뒤 403/ExpiredRequest를 확인했다. TTL을 늘리거나 adapter의 서명을 우회하지 않았다. 로컬 Docker 시계 차이는 유지되는 환경 제약이며 정밀한 만료 시간 비교 시 고려한다. 서명 URL·자격증명·실제 사진은 로그/문서에 출력하지 않았다.

## 추가 실제 흐름과 발견 사항

첫 실제 HTTP+worker 검증에서 합성 PNG/JPEG/HEIF 3장의 R2 PUT 및 조건부 재전송412 → SHA complete 멱등 → 모두 ready → draft 미디어 읽기 → 가짜 생성 review_ready → publish → viewer 결과 읽기 → 다른 개발 사용자404 → album 삭제 API404를 확인했다. 가로 JPEG는 실제 AI 없이 가짜 canvas 변환했다.

삭제 5초 뒤 객체가 없어야 한다는 최초 probe 가정은 비동기 정리와 맞지 않았다. 완료 polling으로 바꾸어 다시 검증하는 과정에서 별도 실제 성능 결함을 확인했다: 삭제된 3페이지의 15asset이 매 poll마다 같은 페이지의 canonical key를 반복 HEAD하여 다음 upload 4개가 120초 안에 검증되지 않았다. 정리 job 자체는 succeeded14/queued2까지 진행했으나 새 validate_upload4개는 queued였다. 검증을 성공으로 간주하지 않고 worker를 잠시 멈춰 불필요 조회를 제한했다. 중복 조회 제거·R2 scan 주기/상한·먼저 job 처리 수정 후 실제 흐름을 다시 확인한다. 기존 local DB/media와 새 R2 queued 작업은 보존했다.

독립 리뷰 I1은 [일시 장애 수정](R2-일시장애-수정.md)으로 수정했다. 실제 PG RED 7failed26passed → GREEN33passed이며 결과 저장 후 응답 유실의 원본 회수도 유지했다. 전체587 회귀 이후 추가된 10개는 이 target에서 검증했다.
