# 병렬 처리 안정성 검증 — 2026-10-17

사용자가 개선 결과를 확인한 뒤 남은 작업 2번(병렬 처리 안정성 검증)을 승인했다. 기준 구현 커밋은 `6135d77`이다. 제품 코드와 동시 실행 설정은 변경하지 않고 검증 시나리오를 추가했다.

## 환경과 범위

- 전용 임시 PostgreSQL 17 DB와 Docker Linux amd64 검증 이미지. QA 사용자 DB·사진·R2 및 실제 OpenAI API를 사용하지 않았다. 추가 유료 호출 0회.
- 작업 한도: DB 전역 caption 4, image_transform 2, optimize 1. 업로드 검증은 worker 프로세스당 1로, worker 2개이면 총 2까지 가능하다.
- AI 응답은 지연을 둔 가짜 provider다. 실제 repository, executor, 비용 장부, worker scheduler, codec subprocess 및 결과 저장 경로를 사용한다. 따라서 실제 OpenAI 응답 시간·요청 제한이나 R2 네트워크 안정성을 증명하지 않는다.

## 시나리오

1. 서로 다른 Python 프로세스 3개에서 단계별 작업 24개를 경쟁 claim. 작업 중복과 DB 전역 동시 실행 한도를 확인한다.
2. 한 사진첩 50페이지의 생성 작업 150개를 두 scheduler가 처리하는 동안 다른 사진첩의 PNG/JPEG/HEIF 신규 업로드 3개를 검증한다. 가짜 provider 호출 수, stage peak, attempt 중복 및 최종 상태를 확인한다. 이 시험의 사진 크기는 작으며 최대 해상도 50장 부하 시험은 아니다.
3. 기존 동시성·fence·삭제·lease 만료·heartbeat·저장 결과 복구·unknown 호출 재전송 금지·비용 장부 복구·storage sweep 독립성 회귀를 재실행한다.
4. 별도 1GiB/no-swap 컨테이너에서 실제 12MP JPEG 및 투명 PNG 정규화와 WebP 최적화를 병행한다. 6개 provider 입력을 모사한 120MiB buffer를 유지한다. 실제 SDK의 base64·HTTP 버퍼 전체를 재현한 것은 아니다. 고밀도 40MP JPEG 경계도 별도 기록한다.

## 실행 결과

| 검사 | 결과 |
|---|---|
| 프로세스 3개·24개 경쟁 claim | caption 4개, image_transform 2개만 claim. 중복 task 없음 |
| scheduler 2개·사진 50장 | 생성 task 150개 모두 succeeded, task별 attempt 최대 1개 |
| AI 호출 수(가짜) | caption 50 + image_transform 25 = 75회. 정확한 3:4 25장은 이미지 AI 생략 |
| 관측 provider 동시 실행 | caption 최고 3, image_transform 최고 2. 설정 상한 4/2 이내 |
| 신규 업로드 중첩 | PNG/JPEG/HEIF 3개 모두 ready |
| 기존 회귀 | 92개 통과. 신규 3개도 fixture 수정 후 최종 통과, 서로 다른 검증 합계 95개 |
| 1GiB 메모리 시험 | 12MP 정규화+최적화 6쌍 완료, peak 727,056,384 bytes = 약 693.4MiB, OOM/oom_kill 0, 71.405초 |
| 큰 입력 보호 | 고밀도 40MP에서 IMAGE_PROCESS_MEMORY_LIMIT. 아래 제한 참조 |

메모리 peak는 fixture 준비·40MP 경계·12MP 병렬 처리 전체 컨테이너 생애의 값이다. 이 측정 범위에서 1GiB의 80% 미만 기준을 통과했다. 실제 DB 연결·SDK serialization·장시간 운용을 포함한 배포 용량 확정 근거로 단독 사용하지 않는다.

실행 로그: `/tmp/mori-parallel-stability-db.log`(최초 94 pass, fixture 오류 1건), `/tmp/mori-parallel-stability-new.log`(수정 후 신규 3 pass), `/tmp/mori-parallel-stability-memory.log`(메모리 성공). 임시 DB·볼륨 및 메모리 시험 컨테이너는 실행 후 제거했다. QA 서버 설정과 API 계약은 변경하지 않았다.

## 발견한 한계

고밀도 합성 40MP JPEG(약 14.2MiB)는 단일 정규화에서도 `IMAGE_PROCESS_MEMORY_LIMIT`으로 거절됐다. 기존 단색 40MP 통과를 모든 40MP 입력 지원 근거로 볼 수 없다. 개별 자식 프로세스의 512MiB 보호 한도가 동작한 결과이며, 서버 전체 OOM과 구분한다. 메모리 한도 상향이나 지원 정책 변경은 이번 검증에서 수행하지 않았다.

첫 신규 테스트 실행의 실패는 시험 fixture의 고정 예약 키 재사용(409)이었고, 서로 다른 파일을 한 batch로 예약하도록 수정했다. 최초 메모리 fixture는 20MiB 입력 제한을 넘었으므로 JPEG 품질과 PNG 노이즈 단계 수를 조정해 허용 입력으로 다시 시험했다.
