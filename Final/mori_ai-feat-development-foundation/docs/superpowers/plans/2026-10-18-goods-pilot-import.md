# 굿즈 파일럿 선별 이식 작업 계획

> **For agentic workers:** 구현 실행 시 `superpowers:executing-plans`를 적용한다. 2026-10-18 사용자가 계획 실행을 승인했다. 유저 플로우 미정 범위는 유지하며 배포 지시는 아니다. 유저 플로우 미정 사항을 임의 확정하지 않는다. 병렬 작업은 실제 배정 시 AGENTS.md와 설치된 Orca 지침에 따라 경계·소유권을 지정한다.

**Goal:** 파일럿의 굿즈 디자인·목업·제작 접수 기능을 선별 이식하고, mori_ai 공통 컴포넌트와 다른 페이지의 디자인을 기준으로 리디자인할 작업 순서와 검증 기준을 마련한다.
**Architecture:** 기존 인증·PostgreSQL·비공개 저장소·worker·비용 장부를 활용하면서 디자인과 제작 주문은 별도 도메인으로 추가한다. UI는 독립 컴포넌트로 준비하고 화면 진입점·앨범 연결·사용자 여정은 후속 결정에 따라 연결한다.
**Tech Stack:** 현재 React/TypeScript/Vite, FastAPI/Pydantic, SQLAlchemy/PostgreSQL, Pillow, local/R2. PDF 엔진과 필요한 신규 패키지는 6단계 검증 후 결정한다.
**Spec:** 2026-10-18 사용자 선택 범위와 본 문서의 확정/제안/보류 구분. 기존 `기능요구명세서.md`, `docs/공통계약-v1.md` v1.6은 현재 사진첩 구현 기준이다. 굿즈 확장 계약은 아직 확정되지 않았다.

## 1. 범위와 현재 단계

이번 요청은 새 하위 시스템을 추가하는 아키텍처 작업의 **사전 계획**이다. 사용자가 유저 플로우를 추가 검토하므로 지금 화면 설계 승인이나 실행 방식 선택을 요구하지 않는다. 아래 경로·모델·API는 작업 분해를 위한 제안이며, 실행 전 0단계에서 최종 계약을 고정한다.

### 사용자가 선택한 이식 범위
- 굿즈 목업, 외곽선 계산, 구멍 선택.
- 디자인 형태별 프롬프트, 상품 예시 이미지.
- 대화형 이미지 생성·수정, 시안 이력과 이전 시안 선택.
- 제작 주문/접수, 제작용 PDF, 메일 전달, 운영자 제작함.
- 굿즈 관련 화면을 mori_ai의 공통 컴포넌트·다른 페이지 디자인에 맞게 리디자인한다(2026-10-18 추가 요청).

### 이번에 자동 추가하지 않는 기능
- 파일럿의 독립 사진첩·QR 공동 편집·공개 감상·NFC 접근 방식.
- 결제·배송 결제·주소 수집·쇼핑몰·재고·자동 제조 발주.
- 기존 사진첩의 스타일 선택·재생성 정책 변경.
- 과거 파일럿 고객·주문·사진·비밀키의 데이터 이전.

### 사용자 플로우 결정 항목 (최신 확정은 10절 우선)
| 결정 | 영향 | 결정 전 가능한 작업 |
|---|---|---|
| 로그인 후 굿즈 시작, 완성 후 앨범 연결 (확정) | 기존 완성 앨범 선택 또는 새 앨범 만들기 | 10절 기준으로 후속 연결 |
| 사진 입력 출처: 새 업로드/앨범 사진/둘 다 | 입력 선택 UI, 참조·삭제 정책 | 소유권 있는 입력 adapter와 fixture 설계 |
| 한 디자인에서 복수 주문 가능한지 | 주문 유일성, 재접수 정책 | 주문 스냅샷과 멱등성 설계 |
| 키링·마그네틱 제공 범위, 크기 옵션 | UI·검증·PDF 치수 | 파일럿 두 종류를 테스트 가능한 모듈로 보존 |
| 단일 시안/3개 비교 제공 여부, 생성 한도 | 작업 묶음·표시·비용 정책 | 단일 생성과 분기 이력부터 설계 |
| 접수 시 이름·연락처 등 입력 항목 | 개인정보·폼·메일 | 최소 주문 구조와 선택 필드 분리 |
| 확정 후 변경/취소, 운영 상태 명칭 | 상태 전이·권한 | 불변 확정본·감사 기록 설계 |
| PDF에 QR 또는 링크가 필요한지 | PDF 내용·접근 권한 | 원화·목업·치수·접수번호 출력 |

파일럿의 6회 생성, 4장 참고 사진, 그림 폭50mm·테두리2mm·탭 거리5mm는 원본 동작의 검증 기준이다. 새 서비스의 상품/운영 정책으로 자동 확정하지 않는다.

## 2. 이식 방식과 기술 판단

**권장: 프론트의 순수 로직은 선별 이식하고 서버는 현재 구조에 맞게 재구현.** 파일럿 전체를 별도 Cloudflare 서비스로 유지하면 인증·비용·운영이 이중화된다. 모든 코드를 처음부터 작성하면 기존 목업과 PDF 동작 검증을 버리게 된다. 권장 방식은 검증 가능한 기존 알고리즘을 살리면서 서비스 경계를 유지한다.

코드 확인 근거:
- 파일럿 기준 커밋: `fb5a3418d2191734d10fcdcb546a77298b57a9f0`. 조사 시 tracked/untracked 변경 없음.
- 원본 폴더: `/Users/choijimin/Downloads/mori-memory-pilot` — 읽기 전용 참고.
- `lib/server.ts`는 Cloudflare env·D1·Sites 인증 헤더에 의존한다. 그대로 붙이지 않는다.
- `backend/models.py`의 MediaAsset은 album_id·page_id가 필수이고 Task.stage는 caption/image_transform/optimize로 제한된다. 굿즈용 가짜 앨범/페이지를 만들지 않는다.
- `backend/generation/budget.py`의 BudgetLedger를 공용 비용 관리 후보로 사용한다. 굿즈 작업과 기존 attempt 관계·호출 정책까지 검증해야 재사용 완료다.
- `backend/worker/jobs.py`의 Job/Outbox 및 lease/fence 규칙을 검토해 새 handler를 연결한다. 기존 사진첩 생성 슬롯과의 자원 경쟁을 검사한다.
- 투명 인쇄 원화는 별도 PNG 자산 정책을 둔다. 사진첩 v1.6의 서비스용 손실 WebP 경로를 그대로 적용하지 않는다.

## 3. 전역 제약

- 현재 QA `.env.qa`, `mori-r2-qa`, Lightsail, 사용자 DB·사진은 변경하지 않는다. 배포·실제 메일·유료 AI 호출은 이 계획 작성의 범위가 아니다.
- 현재 AI 총 승인 상한 USD100/초기 운용 USD5를 늘리거나 새 장부로 초기화하지 않는다. 굿즈 실제 호출 허용 범위는 실행 시 확인한다.
- 기존 사진첩 로그인·업로드·생성·글귀·BGM 동작을 보존한다.
- 사용자 소유권과 운영자 권한은 서버에서 검사한다. Sites 인증 헤더·공개 관리 토큰을 가져오지 않는다.
- 원본 경로를 실행 import하거나 symlink로 의존하지 않는다. 이식 후 mori_ai 단독 실행이 가능해야 한다.
- 사용자 사진·프롬프트·연락처·키·서명 URL을 로그에 기록하지 않는다.
- 라이선스·이미지 출처·글꼴 고지를 확인하고 원본 경로·커밋·변경점·검증을 `docs/재사용조사.md`에 기록한다.
- 현재 checkout의 다른 UI·배포 변경은 건드리지 않는다. 공통 설정·models·migration·lockfile·App.tsx는 총괄 단일 편집이다.

## 3.1 공통 디자인을 활용한 리디자인 기준

기준 문서는 [시안 기반 UI 컴포넌트 분리 계획](2026-10-18-apple-ui-components.md)이다. 참고 화면은 로그인·책장·업로드·생성 진행·글귀 검토·뷰어이며 원본 시안은 `design/references/apple-ui-concepts/`의 6장이다. 구현 시점에 통합된 제품 화면과 승인된 공통 토큰을 우선 적용하고, 오래된 preview의 스타일을 별도 기준으로 복제하지 않는다.

**현재 상태 — 실행 중 갱신:** 사용자가 UI 결과를 머지했고 HEAD `b853a65`에서 공통 컴포넌트와 tokens.css를 확인했다. 신규 굿즈 StylePicker·RevisionHistory·GoodsMockup과 미리보기는 실제 GlassButton·GlassPanel·PhotoFrame·ScreenHeader를 사용한다. 별도 공통 UI 복제품은 만들지 않는다.

| 굿즈 영역 | 참고할 기존 화면 | 공통 부품 재사용 후보 / 리디자인 작업 |
|---|---|---|
| 화면 제목·주요 행동 | 로그인·책장·업로드 | ScreenHeader, GlassButton, IconButton, BottomActionBar로 제목 계층·여백·CTA 표현 통일 |
| 형태 선택·상품 예시 | 책장·업로드 카드 | GlassPanel, PhotoFrame, PhotoThumbnail의 재질·선택 표시 활용. 제품 전체 윤곽이 중요한 예시는 contain 적용 |
| 참고 사진 첨부 | 업로드 | 썸네일·선택·제거·실패 피드백의 시각 규칙 활용. 기존 업로드 훅과 굿즈 API를 혼합하지 않음 |
| 대화·시안 이력 | 글귀 검토·생성 진행 | 입력·보조 문구·상태 표현 통일. 대화 버블·revision 카드는 굿즈 feature에 구성하고 기존 ThumbnailStrip의 책임·props가 맞는 경우 재사용 |
| 생성 상태·실패 복구 | 생성 진행 | 공통 상태 표현과 버튼 사용. 서버가 제공하지 않는 진행률·완료 시각을 꾸며 표시하지 않음 |
| 목업·구멍 선택·확정 정보 | 검토·뷰어 | 그림 전체 표시·집중형 배치, 공통 패널·버튼. 그림 뒤의 배경 재질은 인쇄 원화에 합성하지 않음 |
| 접수 결과·운영자 제작함 | 책장·검토 화면 | 동일 타이포·색·상태·버튼 적용. 운영 목록은 정보 밀도에 맞게 구성하고 모바일 상세도 제공 |

- 색상·타이포·간격·모서리·그림자·유리 효과·포커스는 공통 토큰을 사용한다. 파일럿 `app/globals.css`와 `components/ui/` 전체를 가져오거나 새 UI 라이브러리·폰트 패키지를 추가하지 않는다.
- 공통 UI는 props/callback 기반 표현을 담당하고 인증·생성·주문·메일 상태는 feature 훅/API가 소유한다. 공통 부품 확장이 필요하면 UI 담당자와 단일 편집자로 조율한다.
- PDF·메일은 제품의 명칭·정보 계층을 맞추되 PDF의 인쇄 배율·가독성을 우선한다. 화면용 반투명 효과를 인쇄 문서에 그대로 적용하지 않는다.
- 화면별 normal/empty/loading/error/disabled/selected 상태를 실제 제품 컴포넌트를 사용하는 미리보기로 확인한다. 미리보기 전용 복제 UI는 만들지 않는다.
- 320/390/426/430/1064px에서 가로 넘침·CTA 가림, 긴 한글, 모바일 키보드, safe-area, 최소44px 터치 영역, 키보드 포커스, 대비, reduced-motion·blur 미지원 대체 표시를 검사한다.
- 기능 구현과 별도로 기존 화면과 굿즈 화면의 비교 캡처를 남겨 재질·사진 비율·제목·간격·버튼의 일관성을 검토한다. 유저 플로우 결정 전에는 컴포넌트와 화면 상태 단위의 시각 검토만 진행한다.

제안 모델:
- `DesignSession`: owner, 상품/프로필, 선택한 시안, version. 앨범과 독립적인 식별자.
- `DesignRevision`: 부모 시안 ID, 요청 내용, 입력 참조, 결과 자산, 생성 설정 스냅샷. 수정 결과는 새 행이며 과거 결과 불변.
- `GoodsAsset`: owner, 용도(reference/artwork/preview/pdf), 저장 키, 실제 형식·치수·bytes·hash, 검증 상태. 디자인/주문 연결은 명시적 관계로 관리.
- `GoodsGenerationAttempt`: 작업·호출·예산 예약·결과 저장·unknown 상태. 기존 사진첩 Attempt에 억지로 연결하지 않는다.
- `ProductionOrder`: 확정 시안, 치수·배치, 연락 정보, 원화/미리보기 hash, 제작 상태, version. 확정 자료를 독립 스냅샷으로 보존.
- `OrderEvent` 및 메일 전달 기록: 누가 어떤 상태를 변경했는지, PDF 준비·발송·실패·결과 불명 이력.

서비스 경계 제안: `create_session`, `request_revision`, `select_revision`, `confirm_order`, `render_print_sheet`, `request_order_email`, `change_production_status`. 각 함수는 인증된 actor·명시적 ID·검증된 DTO를 받고, 생성/확정/메일 요청은 멱등 키를 받는다. 정확한 DTO·HTTP 경로·상태명은 0단계 계약에서 고정한다.

## 6. 순서와 병렬화 가능 범위

```text
0 계약·출처 정리
├─ 1 목업·자산 ─────────────────┐
└─ 2 데이터·미디어 → 3 생성·이력 ├→ 4 편집 UI
                    └──────────┴→ 5 주문 → 6 PDF·메일
                                           └→ 7 운영자 제작함
유저 플로우 결정 + 위 기능 검증 완료 → 8 화면 연결·통합
```

- 플로우 결정 전 실제 착수 범위로 권장하는 것은 0단계의 독립 기술 계약과 1단계다. 2~7은 정책에 의존하는 부분을 0단계에서 고정한 뒤 착수한다.
- 1과 2는 계약 고정 후 독립 수행 가능하다. 4는 확정 DTO fixture로 3과 병행 가능하다. 6의 PDF와 메일 adapter는 주문 스냅샷 인터페이스 확정 후 분리 가능하다.
- 4와 7의 제품 리디자인은 공통 UI 결과 인계를 선행 조건으로 둔다. 그 전에는 재사용 매핑·독립 로직·데이터 fixture만 준비한다. 공통 UI 담당자와 동일 파일을 동시에 수정하지 않는다.
- 공통 models/migration, worker 연결, settings·의존성/lock, API 공통 타입·라우터, 핵심 문서는 총괄이 순차 통합한다.

## 10. 사용자 확정 — 굿즈 진입·앨범 연결·사진 교체

2026-10-18 대화에서 확정한 다음 규칙은 앞선 미정 항목보다 우선한다. 문서 반영이며 제품 구현 완료를 뜻하지 않는다.

- 로그인 후 기본 진입 화면은 굿즈 만들기다. 화면 상단 내 프로필 메뉴에 **굿즈 만들기 / 내 디자인 / 내 책장 / 로그아웃**을 제공한다.
- 굿즈 완성 후 **앨범 연결하기**로 이어진다. 이미 완성한 내 앨범 선택 또는 새 앨범 만들기를 제공한다.
- 굿즈 만들기에서 입력 사진은 **1장만** 허용한다. 추가 참고 사진 3장 제안 및 파일럿의 4장 정책은 채택하지 않는다.
- 작업 중 다른 사진을 선택하면 다음 경고와 **취소 / 사진 바꾸고 새로 시작** 동작을 제공한다.

> 사진을 바꾸면 현재 사진과 생성한 시안, 대화 내역, 고리 위치 설정이 삭제됩니다. 새 사진으로 시작할까요?

- 취소하면 현재 사진·시안·대화·고리 위치를 유지한다.
- 확인하더라도 새 사진 검증에 성공한 뒤에만 기존 작업을 초기화한다. 읽기 실패·미지원 형식·검증 실패 시 기존 작업을 유지한다.
- 이미 완성해 저장한 굿즈와 연결된 사진첩은 삭제하지 않는다.
- 구현 검증에는 취소 시 유지, 유효 사진 교체 시 초기화, 무효 사진 교체 시 유지, 교체 전 비동기 응답이 새 작업에 반영되지 않음을 포함한다.

사진 출처·사진 필수 여부·저장·앨범 연결 정책은 아래 11절에서 후속 확정했다. 저장소의 실제 삭제 시점·실행 중 생성 취소 처리는 후속 계약에서 구체화한다.

## 11. 사용자 확정 — 저장·API·AI 연결 정책

이 절은 앞선 자동 저장·재접속 복구·4장 참고·6회 한도·사진 없는 생성 제안보다 우선한다. 구현 완료 기록은 아니다.

- **입력:** 굿즈 시안 생성에 참고할 사진을 기기에서 새로 1장 업로드한다. 모든 형태에서 사진은 필수이며 사진 없이 생성할 수 없다. 내 앨범 사진 선택은 현재 입력 범위에 포함하지 않는다.
- **작업 중 저장 없음:** 미완성 디자인을 자동 저장하거나 재접속 복원하지 않는다. 편집 단계 사이의 정상 이동은 같은 작업을 유지한다. 작업 화면 이탈(메뉴 이동·로그아웃·뒤로가기·새로고침 등) 시 미완성 작업이 사라짐을 경고한다. 취소하면 유지하고 확인하면 폐기한다.
- 브라우저 종료·강제 종료에서 경고나 종료 요청 전송은 보장되지 않으므로, 미완성 서버 임시 자산의 만료 정리를 별도로 설계한다. AI 실행·중복 과금 방지·비용 감사에 필요한 서버 임시 상태/기록은 사용자용 작업 저장·복원 기능과 구분한다. 늦은 AI 응답으로 폐기한 작업이 되살아나지 않아야 한다.
- **시안:** 요청당 1개 생성한다. 수정 결과는 새 시안으로 추가하며 현재 작업 안에서 이전 시안을 선택할 수 있다. 선택 시안의 분기 이력을 사용한다. 사용자 참고 사진 1장과 선택한 생성 시안은 서로 구분한다.
- **제한:** 현재 사용자별 생성 횟수·비용 제한을 두지 않는다. 제안했던 6회 제한은 채택하지 않는다. 추후 제한 도입은 필수 후속 작업으로 남기고, 횟수·비용 계측 및 설정 가능한 제한 경계를 마련한다. 이 결정만으로 실제 개발 검증 호출의 기존 총 $100 승인 예산을 무제한으로 변경하거나 유료 호출을 실행하지 않는다.
- **모델:** 추억앨범에서 쓰는 이미지 모델과 동일한 모델을 초기 기본값으로 사용한다. 저장소 기준 backend/settings.py와 .env.example의 현재 기본값은 gpt-image-2다(운영 환경값은 이번 확인 대상 아님). 모델명은 UI·도메인에 고정하지 않고 adapter/설정으로 교체 가능하게 하며 각 요청에 사용 모델·프롬프트 버전을 기록한다. 기존 공급자 코드의 모델 고정 검증도 후속 구현에서 조정한다.
- **완성:** 굿즈 디자인 완성이 완료 기준이다. 사용자가 완성한 디자인은 영속 저장하고 **내 디자인** 목록에서 볼 수 있다. 앨범 연결 및 제작 요청은 별도 단계이며, 연결 전에도 완성 디자인은 보존한다.
- **앨범:** 굿즈당 앨범 1개를 연결한다. 기존 완성 앨범 선택 또는 새 앨범 만들기를 제공한다. 제작 요청 시작 전에는 변경 가능하고, 제작 요청 시작 후 다른 앨범으로 변경할 수 없다. 연결 변경과 제작 요청 시작의 경쟁은 서버 트랜잭션으로 차단한다. 제작 요청 시작의 정확한 상태 전이/API는 주문 계약에서 구체화한다.
- **메뉴:** 상단 프로필 메뉴는 굿즈 만들기 / 내 디자인 / 내 책장 / 로그아웃이다. 내 디자인은 완성 굿즈 목록이며 미완성 작업 목록은 제공하지 않는다.

후속 검증: 사진 없는 요청 거부, 이탈 취소/확인, 새로고침 후 미완성 복원 없음, 폐기 후 늦은 응답 무효화, 완성 저장의 멱등성·소유권, 내 디자인 목록 격리, 제작 요청 시작 후 앨범 변경 거부, 모델 교체 설정, 제한 미적용 시에도 비용 기록 유지.
