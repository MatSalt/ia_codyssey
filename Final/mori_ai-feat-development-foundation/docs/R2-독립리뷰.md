## I1 — 생성 전 R2 일시 장애가 복구 불가능한 unknown이 됨 (Important / P2)

**위치:** `backend/generation/fake_adapter.py:74`, `:124–130`. 연결되는 기존 분기: `backend/worker/runner.py:192–208`, `:267–280`.

R2 모드의 가짜 caption 또는 image_transform 작업이 실행될 때 최초 `_verify()`가 입력 checksum/HEAD를 조회한다. 여기서 `StorageUnavailable`을 그대로 전파하도록 변경했지만 Runner는 이 예외를 확실한 미발송 실패로 인식하지 않는다. `requires_ai_call=True`인 이 단계들은 이미 `_mark_sent()`를 거쳐 `accepted_or_unknown`이므로 `unknown`, `AI_RESULT_UNKNOWN`, `safe_to_retry=False`로 끝난다.

이 장애는 caption 생성 또는 image transform 실행 **전**에 발생한다. 따라서 회수할 envelope/결과 blob이 없다. R2 연결이 복구돼도 caption의 `recover_original()`은 항상 None이고, image_transform도 원래 output 참조가 없으므로 회수하지 못한다. scanner는 계속 unknown으로 유지하고 공개 resume도 unknown을 재발송하지 않아 사용자는 기존 사진첩을 복구할 수 없다. 정상적인 일시 저장소 장애 한 번으로 생성 흐름이 막히는 문제다.

**재현 근거:** 네트워크 없는 `mori-ai:r2-tests`에서 실제 `FakeExecutor.execute/_verify`, 실제 `Runner.run_once`를 실행했다. DB claim/transaction/settlement와 `_context`만 메모리 대역으로 제공하고, store.checksum이 `StorageUnavailable`을 던지게 했다. caption/needs_ai=True, 기존 accepted_or_unknown 상태를 사용했으며 ResultStore.save는 호출 시 실패하도록 구성해 결과 저장이 없음을 확인했다. 실제 출력과 assertion 통과 결과:

```text
{'before_generation_R2_outage_status': 'unknown',
 'safe_to_retry': False,
 'error': 'AI_RESULT_UNKNOWN',
 'caption_original_recovery': None}
```

이는 DB 통합 재현을 주장하는 결과가 아니라 현재 예외→상태 분기를 독립적으로 실행한 최소 mock 재현이다. `recover()`의 unknown 유지와 API 재개 불가는 해당 코드 및 공통계약의 unknown 정책으로 확인했다.

**수정 방향:** 결과 생성 전이라고 증명할 수 있는 초기 입력 검증/다운로드 실패는 미실행·재시도 가능 오류로 전달한다(예: `FakeExecutionError(..., safe_to_retry=True)`의 기존 not_sent 처리). `_verify()`는 변환 후에도 호출되므로 모든 StorageUnavailable을 일괄 미발송으로 바꾸지 말고 경계를 구분해야 한다. 이미 보존된 결과/envelope의 응답 유실에는 원래 결과 회수 정책을 유지한다. 실제 DB 회귀에는 caption/image_transform 최초 checksum 503 → R2 복구 → 안전한 재개 성공을 추가할 것을 권한다.

## 확인한 경계

- 발급·complete는 owner/album/page/asset 연결을 검사한다. ready·현재 연결된 공개 role만 GET을 발급하고 canonical key를 재검사한다. R2 모드의 local private PUT/read는 404다.
- prefix는 Settings에서 안전한 segment와 trailing slash를 강제한다. low-level object/envelope key는 canonical UUID namespace를 제한한다. 기존 서비스 자원으로 자동 이관하는 경로는 없다.
- complete는 원격 크기·SHA를 DB lock 밖 thread에서 확인한 뒤 lock 안에서 삭제/만료를 재확인한다. validating/ready replay의 다른 SHA는 409다. 조건부 PUT 412나 TypeError/timeout은 frontend의 성공 확정이 아니며 같은 File SHA로 complete를 확인한 뒤 marker를 남긴다.
- 실제 설치 boto3를 합성 credentials로 오프라인 presign하여 `X-Amz-SignedHeaders=content-length;content-type;host;if-none-match`를 확인했다. JS가 Content-Length를 직접 설정하지 않고 외부 R2에 앱 CSRF를 붙이지 않는 경로를 확인했다. 실제 브라우저/R2 CORS 성공을 뜻하지 않는다.
- 원격 HEAD/GET가 원장이고 파일·envelope 크기 상한 및 stream close가 있다. 캐시의 기존 bytes를 원격 성공으로 대신하지 않는다. immutable write 충돌은 원격 SHA가 같은 경우만 수렴한다.
- validation의 원격 일시 장애는 retry_wait로 전파된다. SDK I/O는 thread 및 DB lock 밖에 놓였다. 삭제 tombstone sweep가 source 404 뒤 다른 canonical role도 확인하며 늦은 PUT/파생본을 다시 정리한다. 기존 fence/owner 검사는 유지됐다.
- MPO 주프레임과 HEIF 8비트 SDR 주이미지 예외는 좁게 적용됐다. ICC 길이·태그 범위·중복·세 채널 TRC·sRGB 계수 검사가 있고 PQ/HLG/highbit 및 주이미지 HDR 신호 거부를 유지한다. auxiliary 메타데이터 주입 시험은 실제 사용자 HEIC 컨테이너 검증과 구별되어 있다.
