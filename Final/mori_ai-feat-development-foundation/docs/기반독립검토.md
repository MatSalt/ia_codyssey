- 사용자 영향: 정상 SDR PNG가 성공 응답을 받으면서 표시 밝기·색상이 달라지고, 같은 잘못된 파생본이 글귀/이미지 AI 입력이 된다. 실패를 명시하는 현재 HEIF 광색역 보호와 달리 잘못된 색상으로 조용히 통과한다.

- 검증 상태: 정적 finding. 새 입력을 만드는 재현 실행은 하지 않았다.

### I3 — Important: RGB/RGBA 16bit PNG는 고비트/HDR 보호를 우회할 수 있음

- 위치: `backend/media/normalize.py:58`, `backend/media/normalize.py:66`, `backend/media/normalize.py:72`, `backend/media/normalize.py:74`; 검사 공백: `backend/tests/media/test_normalize.py:109`의 고비트 검사는 grayscale `I;16` 경로뿐이다.
- 재현 조건: IHDR bit depth=16, color type=2 또는 6인 PNG를 입력한다. 특히 ICC/XMP 없이 cICP에 PQ/HLG 전달특성을 선언한 자료는 현재 검사하는 HEIF nclx/HDR key가 없다.
- 근거: 선택 버전과 같은 [Pillow 12.3 PNG 소스](https://pillow.readthedocs.io/en/stable/_modules/PIL/PngImagePlugin.html)의 `_MODES`에서 16bit truecolor는 공개 mode RGB/RGBA와 rawmode RGB;16B/RGBA;16B로 열린다. IHDR parser는 제품 코드가 보는 info.bit_depth를 만들지 않는다. 그러므로 기본값 8과 RGB/RGBA mode로 보호 조건을 통과하고, load에서 8bit 채널로 축소된다. 이 소스에는 PNG cICP 해석 경로도 없어 nclx 검사로 이를 포착할 수 없다. 제품 코드와 decoder 소스에 근거한 정적 추론이다.
- 사용자 영향: 보고서에 명시한 “검증된 tone mapper가 없으므로 고비트/HDR은 명시적 실패”라는 경계가 PNG truecolor에서 성립하지 않는다. HDR 자료가 비트 깊이 축소만 거쳐 정상 WebP로 통과할 수 있다. 일반 16bit SDR가 모두 HDR라는 뜻은 아니다.
- 수정 방향: 디코딩 전 PNG IHDR 원본 bit depth와 색상/transfer 선언을 확인하거나 이를 보존하는 decoder 정보를 사용한다. 미검증 경로는 명시적으로 실패시키고, 실제 tone mapping을 도입할 때 별도 합격시킨다. 16bit RGB/RGBA와 cICP HDR fixture를 기존 grayscale 테스트와 별도로 추가한다.
- 검증 상태: 정적 finding이며 실제 HDR PNG 출력 비교는 미실행이다. 실제 iPhone HEIC/P3 합격 여부와는 별개의 경로다.

- scripts: `set -euo pipefail`/`sh -ec`, pytest/codec 선행 실패 전달, fixture/scripts read-only mounts, 전용 DB 이름/version gate, 임시 자원 cleanup을 직접 읽었다. codec/load는 MORI_VERIFY_TEST_IMAGE 또는 MORI_VERIFY_IMAGE 뒤 `-tests`, DB 검증은 MORI_VERIFY_TEST_IMAGE, isolation은 MORI_VERIFY_IMAGE를 사용한다. DB 명령이 runtime override를 자동 추론한다고 주장하지 않는다. 위 M1은 제품 media 환경변수 전달의 별도 공백이다.
