## 원인 확인과 수정

**I1: 완료된 cleanup 이후의 늦은 파일 확정을 재탐색할 원장이 빠져 있었다.** 기존 사후 PUT 재검사는 요청이 살아 있을 때만 파일을 지웠으며, deleted_at이 있는 asset은 기존 미완료 scanner에서 제외되었다.

기존 worker가 주기적으로 부르는 `scan_incomplete_uploads()`에 별도의 tombstone sweep을 연결했다. asset.deleted_at, album.deleted_at, page.removed_at을 DB의 durable 근거로 삼고 UUID keyset cursor로 한 회 최대 100개를 검사한다. 기존 24h 미완료 업로드 후보는 별도로 최대 100개다. cursor는 깨끗한 행·잘못된 key도 지나가며 끝에서 순환하고, 재시작하면 처음부터 다시 시작한다. 완료된 cleanup job이나 같은 deleted_at이라는 이유로 tombstone을 영구 제외하지 않는다.

현재 canonical 파일이 있는지 **DB 잠금 밖** thread에서 확인한다. 파일이 있으면 짧은 album 잠금 transaction에서 owner/album/page/role/key 및 cleanup eligibility를 재확인한 뒤 기존 cleanup_asset job을 멱등 재예약한다. 실제 삭제 handler는 기존 fence·lease 검사를 유지하고 파일 I/O는 transaction 종료 뒤 수행한다. DB 미연결 normalized/thumbnail은 삭제된 페이지의 canonical source/asset anchor로 함께 정리한다. Task/Attempt·활성 Page 참조와 validating/복구 입력 보호는 같은 eligibility 함수로 유지하며 attempt JSON envelope 경로는 다루지 않는다.

실제 재현은 HTTP PUT 앞 2 bytes에서 스트림 대기 → DELETE 202 → outbox/cleanup 완료와 deleted_at 확인 → 남은 2 bytes 전송·원본 link 확인 → 실제 HTTP request task.cancel() 순이다. 이어 새 ValidationWorker와 실제 Runner maintenance/scanner를 실행해 source와 미연결 normalized가 사라지는 것을 검사한다. 같은 tombstone에 source를 다시 써도 완료된 job이 재예약되어 정리된다. 단순 route except/finally 수정으로 crash를 해결했다고 주장하지 않으며, 이번 수정은 periodic DB tombstone 재탐색으로 수렴한다.

**I2: 페이지 제거가 batch terminal 전이를 확정하지 않았다.** 제거 대상 upload의 batch를 찾아 같은 album 잠금 transaction에서 제거/flush 뒤 finish_batch를 수행한다. 남은 active 페이지가 terminal이면 날짜순 정렬·연속 position·cover를 함께 반영하고 manual은 유지한다. 아직 terminal이 아니면 현재 순서의 빈 position만 메운다. reserved/validating 마지막 페이지와 date/manual 4조합을 실제 HTTP·codec·DB에서 검사했다.

**I3: UI의 신고 MIME 조건이 지원 HEIC/HEIF를 막았다.** 기존 검사식을 helper로 추출한 상태에서 실제 Node File의 binary MIME 입력 실패를 먼저 확인했다. application/octet-stream은 지원 확장자 검사에 통과한 `.heic/.heif` 조합에서만 예외로 받는다. `.png/.jpg` binary MIME, 임의 unknown MIME, 위장 확장자, 혼합 invalid 파일과 개수/용량 초과는 계속 거부한다. 빈 MIME과 설정에 있는 정상 image MIME은 유지했다.

**M1: complete/정규화/정렬의 공개 변경이 version에 반영되지 않았다.** reserved→validating/expired와 ready/rejected에서 page/album revision을 같은 transaction에 반영한다. position이 실제 바뀐 페이지만 증가하고, 같은 transaction의 ready+position 변경은 한 번만 증가한다. 예약 중 기존 페이지 만료, scanner 만료, 제거 후 position 변경도 포함한다. 최초 date→manual은 album만 바뀔 수 있고, 이미 manual인 동일 순서 재전송은 증가하지 않는다. terminal complete, 조회, media-access, Idempotency replay의 no-op은 증가 0이다.

기존 codec/delete와 batch 테스트의 예상 version 3/5/6은 complete 전이를 빠뜨린 값이었다. reserve→complete→terminal의 정확한 새 값(단일 ready/rejected album=4, 두 batch 검증 뒤 album=7 등)으로 교정하고 DELETE 성공 상태 assertion 및 페이지별 revision을 추가했다. assertion을 삭제하거나 범위를 느슨하게 바꾸지 않았다.

## 남은 경계와 인계

- 작업자 검증은 로컬 HTTP/PG·실제 synthetic codec·실제 HTTP task 강제 취소와 새 worker/scanner 인스턴스 복구다. 이 late PUT 검사에서 OS 프로세스 SIGKILL을 새로 실행한 것은 아니다. 기존 validation process kill/restart 검사는 전체 224개에 유지되어 있다.
- 정리는 worker가 계속 실행될 때 bounded sweep 순환으로 수렴한다. 늦은 파일의 즉시 물리 삭제를 보장하지 않으며 DB/API의 삭제 후 404 경계는 유지한다. 범위는 DB로 식별되는 canonical source/derived object이며 임의 경로나 attempt envelope를 일괄 삭제하지 않는다.
- 실제 OAuth/R2/AI·모바일 실기기·HDR 품질·배포는 실행하지 않았다. 최종 Linux amd64 clean Docker 재현·브라우저 합류·환경 격리·commit/통합 판정은 총괄 소유다.
- 코드/계약 밖 변경 요청은 발생하지 않았다. 이번 수정으로 공개 DTO 필드, migration, 공통계약 version을 바꾸지 않았다.
