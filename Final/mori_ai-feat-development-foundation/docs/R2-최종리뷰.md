## 정리 공정성·동시성 확인

- `backend/worker/__main__.py:37`: validation/cleanup job을 maintenance와 sweep보다 먼저 실행한다. 각 예외 경계를 분리하여 스캔 오류가 다음 poll의 job 처리를 건너뛰게 하지 않는다. cleanup보다 validate를 우선하는 별도 큐 정책을 추가한 것은 아니다.
- `:50`: R2에서 한 개의 `storage_scan` 참조만 관리한다. 진행 중에는 새 작업을 만들지 않고 완료 후 result를 읽어 오류를 회수한다. 성공·실패 모두 완료 확인 시점부터 30초 후 다음 scan을 시작한다. tombstone 및 오래된 upload 후보는 각각 10행 상한이며 시간 상한이나 전체 합계 10행을 의미하지 않는다. local은 기존 100행 정책이다.
- `backend/uploads/validation.py:216`: 존재/부재 캐시는 scan 호출 지역 변수다. 동일 페이지의 canonical 키를 한 scan에서 중복 HEAD하지 않으며 다음 호출에서는 다시 원격 상태를 확인한다. source 404가 다른 파생 키 조회를 중단하지 않는다. UUID cursor는 wrap/restart 때 재방문하며 완료된 cleanup도 late PUT 발견 시 재예약 가능하다.
- `validation.py:208`, `:218`, `:243`: DB는 매 작업마다 새 session을 만든다. 조회 session을 닫은 뒤 원격 HEAD를 수행하고, enqueue 직전에 새 transaction에서 album lock·tombstone·소유권·canonical 키를 다시 검증한다. foreground·heartbeat·background가 같은 AsyncSession을 공유하지 않는다. foreground cleanup도 원격 삭제 동안 DB lock을 유지하지 않는다.
- `__main__.py:80`: 종료 시 scan을 cancel하고 await한 뒤 engine을 dispose한다. 이미 시작한 `asyncio.to_thread`의 동기 SDK 요청은 즉시 중단되지 않지만 coroutine은 후속 key 조회나 DB enqueue로 진행하지 않는다. 현재 R2 SDK의 connect 10초/read 30초·1 attempt 제한은 유지된다. 즉시 스레드 종료 보장은 하지 않는다.
- 느린 scan stub에서 foreground job 4회 처리, scan 1개 유지, 종료 시 cancellation 회수를 직접 확인했다. StorageUnavailable/TimeoutError 완료 경로와 local 경로도 통과했다. 실제 R2 지연의 절대 시간 보장은 이 테스트 범위 밖이다.
