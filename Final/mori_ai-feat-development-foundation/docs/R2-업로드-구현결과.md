## 구현

- 예약은 `Signer.upload_url(key,path,entity,expires,mime,declared)` 결과 URL·헤더를 반환하고 `validation_config.storage_mode`를 기록한다. 기존 멱등 요청·소유권·버전·900초 만료를 유지한다.
- complete body는 optional lowercase SHA256와 extra forbid를 적용한다. local `{}`는 유지하며 R2는 체크섬이 필수다. 소유권·삭제를 먼저 조회하며 만료 응답은 기존 semantics를 유지한다.
- 원격 stat/checksum은 DB transaction 밖에서 `asyncio.to_thread`로 호출한다. 선언 크기 불일치는422, SHA256 불일치는409, remote404는422 UPLOAD_NOT_READY, StorageUnavailable은 재시도 가능한503이다. validating/ready/rejected 재요청도 보관된 SHA256와 대조한다.
- local private PUT/read는 R2 mode에서404다. media-access 및 앨범 목록·상세 access_entries는 현재 공개 가능한 asset을 다시 조회하고 canonical key를 검증한 뒤 `read_url`에 key를 넘긴다.
- `putFile.ts`의 `completionBody(file,headers)`는 조건부 R2 업로드의 원래 File SHA256를 WeakMap에 한 번 계산·보관하며 20MiB와 Web Crypto 가용성을 검사한다. `putFile(url,file,headers,signal)`는 조건부 헤더가 있는412만 complete 검증으로 넘기며 다른 비정상 응답·network loss는 실패한다.
- useUploads는 PUT marker가 있거나 서버가 validating이라 PUT를 건너뛰어도 complete에 같은 File 체크섬을 보낸다. 기존 intent·예약·mutation key 보존과 complete 성공 뒤 marker 기록을 유지한다.

## 후속: 조건부 PUT 응답 유실 회수 (2026-10-16)

Task task_bc7ad2a91523 / Dispatch ctx_8bd6b5424e87. 이 절은 위 최초 구현의 network loss 즉시 실패 설명을 갱신한다.

가설: 저장에 성공한 PUT 응답이 유실되거나 조건부412 응답에 CORS 헤더가 없으면 브라우저 fetch는 상태코드 대신 TypeError를 반환할 수 있다. 실제 R2에서412 CORS 헤더 부재를 관찰한 것은 아니며, 이번에는 가능한 환경 경계를 네트워크 stub으로 재현했다.

변경:

- 조건부 `If-None-Match:*` PUT에서만 TypeError·TimeoutError·412를 서버 검증 후보(`verify`)로 반환한다. 이 반환은 성공 확정이 아니다. 다른 HTTP 오류와 local 네트워크 오류는 기존처럼 throw한다.
- `uploadStep`은 useUploads가 실제 사용하는 전송·완료 상태 처리다. 원래 File SHA256를 서버 complete에 보내고 완료 확인 성공 후에만 R2 put/complete marker를 기록한다. complete422·409 등 실패 때 기존 put marker도 제거하여 다음 재시도에서 같은 예약 URL과 File의 PUT를 다시 실행할 수 있게 한다.
- 사용자 AbortSignal이 취소되면 검증 후보로 처리하지 않고 throw하며 complete를 시도하지 않는다. hashing/status/PUT/complete 사이에도 취소를 확인한다.
- `putFile` 반환형은 `Promise<'uploaded'|'verify'>`, 신규 `uploadStep(upload,file,progress,signal,putHeaders,statusCallback,completeCallback)`를 같은 모듈에서 export한다. 기존 Node argv2 모듈 경로는 그대로다.

검증:

- RED `/tmp/mori-r2-recovery-red.log`: 기존 TypeError가 throw되는 실패와 신규 공용 uploadStep 부재를 확인했다.
- GREEN `/tmp/mori-r2-recovery-green.log`: helper tsc, Node11개, 전체 frontend `tsc --noEmit`·Vite build 통과. 기존 frontend Docker stage 의존성을 사용했고 호스트 설치는 없었다.
- 마지막 검증 `/tmp/mori-r2-recovery-final.log`: validating 상태 재시도도 추가해 Node12개 통과. 검사 대상은 저장 후 TypeError/TimeoutError→SHA 확인 성공, 미전송 TypeError 및412→complete422→다음 실제 PUT 성공,409 때 marker 미확정 및 기존 marker 제거, 사용자 abort 때 complete 미호출,local 오류 유지,validating에서 PUT 없이 원래 SHA 확인이다. 네트워크 호출 순서·원래 File/URL·완료 상태를 검사한다.
