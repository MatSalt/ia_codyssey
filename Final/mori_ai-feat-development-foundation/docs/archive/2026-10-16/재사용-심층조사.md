## 1. 기술 결정에 앞서 볼 결론

재사용 가치가 큰 것은 기존 제품 전체보다 **OAuth provider의 통신 부분, 저장소의 I/O·서명 부분, durable workflow의 경쟁·복구 경험, 뷰어의 작은 입력 유틸리티**다. 동일 언어·라이브러리를 선택해도 새 계약의 서버 세션, asset 중심 접근, 정확한 3:4 분기, unknown 재호출 금지, 삭제와 결과 연결의 경쟁 해결을 새로 구성해야 한다.

소스가 Python/FastAPI·SQLAlchemy/PostgreSQL·Redis Streams, React/TypeScript·Vite를 쓴다는 사실은 새 서비스의 채택 결정이 아니다. 공통계약이 현재 PostgreSQL repository와 Pillow/pillow-heif를 명시하므로 다른 DB·언어를 선택하려면 계약과 검증 계획까지 조율해야 한다. 반면 Redis·R2·Vite는 이 조사로 확정되지 않으며 큐·저장소·frontend 도구를 바꿔도 공개 DTO를 유지할 수 있다.

## 2. 인증: provider만 좁혀 가져오기

근거: [Google provider](/Users/choijimin/dev/active/moriai/backend/core/auth/providers/google_oauth.py), [Kakao provider](/Users/choijimin/dev/active/moriai/backend/core/auth/providers/kakao_oauth.py), [social login](/Users/choijimin/dev/active/moriai/backend/features/auth/services/social_login.py), [DI](/Users/choijimin/dev/active/moriai/backend/features/auth/dependencies.py), [AuthService](/Users/choijimin/dev/active/moriai/backend/features/auth/service.py).

- Google 직접 의존성은 `httpx`, `google.auth.transport.requests`, `google.oauth2.id_token`, `core.config.settings`다. 코드 교환의 `redirect_uri`가 `postmessage`로 고정되어 새 `/auth/google/start → callback` 흐름과 다르다. ID token audience·issuer 검증은 참고할 수 있으나 동기 Google 검증 호출을 async 함수 안에서 수행하므로 새 실행 모델에 맞춰 분리해야 한다.
- Kakao 직접 의존성은 `httpx`·settings다. 코드 교환은 설정 redirect URI를 사용한다. `get_user_info`는 이메일 없으면 실패하며 이름·전화번호 정규화와 native access token 앱 ID 검증까지 제공한다. 새 사진첩이 이 개인정보와 native 흐름을 요구하는 것은 아니다. provider subject를 문자열로 반환하는 부분만 선별하고 이메일 필수 정책을 별도로 결정한다.
- 간접 체인은 `dependencies → social_login/AuthService → UserRepository/SQLAlchemy User → JWTManager/RefreshSessionStore → CacheService`이며 DI가 Apple cipher·Resend email·credits도 조립한다. AuthService에는 가입 크레딧 지급과 회원탈퇴 use case까지 있다. provider 파일 두 개의 통신 부분을 추출하면 이 체인을 대부분 피할 수 있다.
- `social_login.py`는 provider+subject로 기존 identity를 찾고 이메일 충돌은 자동 병합 대신 오류로 처리한다. 이 원칙은 유용하지만 기존 User schema·이메일 검증 정책·세션 발급은 가져오지 않는다.

**판정:** Python backend라면 R01만 설정·HTTP client를 주입하는 adapter로 수정 이식한다. R02는 신규 session repository·CSRF·OAuth state 일회성/만료·내부 return_to 허용목록·동의 기록과 함께 작성한다. 다른 언어 또는 auth framework를 선택하면 endpoint·응답 검증·실패 사례를 참고하고 소스는 신규 작성한다. 대상 제안은 `backend/auth/adapters/`, `backend/auth/application/`이며 확정 경로가 아니다.

추가 확인 조건: state 저장과 callback 소비의 원자성, 로그인 거절·중복 callback·잘못된 audience·issuer, 이메일 미제공 Kakao 사용자 정책, provider subject 분리와 동일 이메일 충돌, 세션 철회·CSRF·쿠키 속성. 원본 `backend/tests/unit/auth/{test_google_oauth,test_kakao_oauth}.py`는 사례 후보이며 이번에는 읽기 기반 조사만 했고 테스트를 실행하지 않았다.

- backend의 HEIC/HEIF·DateTimeOriginal·ImageCms 검색과 requirements에서 새 서버 HEIF decoder·촬영일/색상 정규화 pipeline을 확인하지 못했다. 이는 전 저장소에 구현이 없다는 증명이 아니다. `test_photo_upload.py`에 raw HEIC 업로드 거절 사례가 있어 원본 동작을 새 요구 충족으로 취급하면 안 된다.

**판정:** hash/asset metadata 계산과 WebP encoding 형태는 수정 이식 후보, 원본 보존→실파일 검증→primary image·방향·색상·날짜 추출→WebP 정규화는 신규 작성. Python/Pillow를 유지하면 인코딩 지식 재사용이 쉽고, 다른 언어라면 동등 codec·HEIF/HDR 정책을 확인하고 계약을 조율한다. 배포 이미지에서 HEIC 10bit/HDR·decoder·WebP magic bytes·contain·3:4 판별을 추후 실제 검증해야 한다.

## 4. workflow: 모델 복사보다 실패 방지 패턴 재사용

근거: [workflow contracts](/Users/choijimin/dev/active/moriai/backend/core/workflow/contracts.py), [retry](/Users/choijimin/dev/active/moriai/backend/core/workflow/retry.py), [queue](/Users/choijimin/dev/active/moriai/backend/core/workflow/queue.py), [SQLAlchemy repository](/Users/choijimin/dev/active/moriai/backend/features/creator_book/infrastructure/persistence/sqlalchemy_workflow_repository.py), [recovery scanner](/Users/choijimin/dev/active/moriai/backend/features/creator_book/application/workflow_recovery_scanner.py), [Redis queue](/Users/choijimin/dev/active/moriai/backend/features/creator_book/infrastructure/queue/redis_workflow_queue.py).

R05의 contracts/retry/queue는 표준 dataclass·StrEnum·Protocol 기반으로 외부 패키지 결합이 작다. 하지만 QueuePort가 task_id 하나가 아닌 StageCommand와 ProviderTerminalEvent를 전송하고 command에 input_ref·metadata를 포함한다. RetryPolicy는 실행 코드가 아닌 protocol이므로 파일 복사만으로 재시도 정책이 구현되지 않는다. 새 task/attempt/dispatch_state DTO를 먼저 정의하고 필요한 작은 enum/dataclass 형태만 수정 이식하는 편이 낫다.

R06 repository의 직접 의존성은 SQLAlchemy async, PostgreSQL insert, workflow contracts/redaction, creator domain stages/statuses/state_machine, creator persistence models/ports, storybook Book/Dialogue/Page·page_membership이다. 간접적으로 projection, revision 사용량, 기존 책 스키마로 이어진다. claim과 outbox 조회에 `FOR UPDATE SKIP LOCKED`, 상태 전이에 expected_status·attempt 조건, outbox dedupe에 PostgreSQL conflict 처리를 사용한다. transaction 안의 task/outbox 기록과 outbox stale publish 재선점은 재사용할 설계 근거다. 새 계약의 album lock·task fence·삭제 후 늦은 결과와 동일하다고 단정하지 않는다.

recovery scanner는 stale submitting task를 찾고 stage·metadata에 따라 재시도 또는 recovery_required로 나눈다. 간접 의존인 `revision_usage_settlement`는 이번 사진첩에 필요 없는 정산이다. 새 서비스에서는 전송 여부가 unknown이면 resume으로 새 유료 호출하지 않고 보존 파일·provider 결과 회수를 먼저 확인해야 한다. 원본 scanner 전체를 가져오는 대신 새 상태 전이에 대응해 작성한다.

Redis queue는 주입 redis의 xadd를 사용하지만 `domain.stage_queues`와 `creator.*` envelope/stream 이름에 결합한다. 기존 worker entry는 character sheet와 creator runtime을 함께 조립한다. **큐를 유지해도 새 task_id 알림 adapter·consumer를 작성**하고, DB polling 또는 다른 큐를 선택하면 Redis stream 구현을 버려도 outbox·claim·복구 원칙은 유지한다. PostgreSQL+SQLAlchemy라면 SQL 패턴 재사용이 가장 쉽고, 다른 ORM이면 transaction/lock/upsert를 다시 구현한다. migration 체인은 가져오지 않는다.

대상 제안은 `backend/generation/{domain,application,repository}/`와 `backend/dispatcher/`다. 추후 조건은 중복 생성·동시 claim·lease 만료 후 stale 결과·outbox 재발행·worker 종료·unknown·삭제 경쟁의 계약 시나리오이며 이번에 실행하지 않았다.

- image command는 character_sheet를 기본 feature로 삼고 provider route·webhook·여러 reference·output profile·storage recovery를 포함한다. profiles의 OpenAI legacy output은 PNG, 일부 1536×1024 또는 1536×768이다. Runware legacy만 768×1024 WEBP다. 새 WebP 입력/출력·정확한 3:4 계약을 이 파일들로 충족한다고 보고하면 안 된다.
- `ImageStorageRecoveryPort.reserve_save/record_failure`는 attempt 소유 저장 예산을 checkpoint하고 AI 재전송을 허가하지 않는 경계다. executor `_save_with_retry`의 저장 재시도와 provider 제출 재시도를 구분하는 경험은 유용하다. 다만 새 계약의 응답 즉시 attempt별 파일 보존·fence 연결·orphan cleanup까지 그대로 보장하는지는 별도 설계·검증해야 한다.
- **정책 충돌:** `classify_media_submit_outcome`의 UNKNOWN 분기는 `fallback_allowed=True`, `task_retryable=True`다. executor에는 일부 unknown 제출을 retryable=False로 반환하는 별도 분기도 있다. 전체 경로를 동일 안전성으로 취급할 수 없으므로 새 `unknown_result/accepted_or_unknown` 정책으로 신규 분류하고 전송 증거만 참고한다. safety rejection도 공통 분류에서 fallback을 허용하는 경우가 있어 새 policy_blocked 정책으로 재평가한다.
- image_analysis는 사진 bytes/MIME을 Gemini에 전달하나 어린이 동화용 people/objects/background/action/mood/confidence/warnings JSON을 생성한다. 직접 의존성은 google-genai(지연 import), httpx/Pydantic, AI base와 settings다. 예외를 retryable·auto_retry로 바꾸며 MIME 기본값은 JPEG다. 사진첩의 원본 정규화본 기반 한 문장·NFC code point 길이·빈 사용자 글귀 허용 정책과는 다르다.

**판정:** executor/analysis 전체는 참고 신규 작성. 같은 provider를 선택한 경우 HTTP payload·오류 증거 parsing 일부를 수정 이식할 수 있으나 model·SDK 버전·timeout·자동 retry를 다시 확인한다. 글귀 provider/model은 이 조사로 선택하지 않는다. 이미지 adapter와 caption adapter는 bytes·usage·request ID·dispatch_state만 반환하고 상태·저장·재시도 정책은 application/worker가 소유한다. 3:4 변환 생략은 adapter의 임의 판단이 아니라 정규화 dimensions에 따른 task 분기다. 대상 제안은 `backend/ai/adapters/`다.

## 9. 한계·채택 전 조건

1. 파일 본문·선별 import·연결된 주요 구현·architecture 문서를 읽었지만 전수 transitive dependency closure를 계산하지 않았다. 동적 import·runtime DI·provider별 모든 분기를 검증하지 않았다. 읽은 import 체인과 추론한 추가 비용을 구분했으며 실제 성능·보안·호환성 보증은 없다.
2. 원본 HEAD·working tree 상태와 문서 링크의 파일 존재를 정적으로 확인했다. 테스트·build·lint·runtime·OAuth·DB·bucket·AI는 실행하지 않았다. 코드 실행 검증은 후속 승인 범위다.
3. `rg --files -g '*LICENSE*' -g '*NOTICE*'`에서 저장소 고지 파일을 찾지 못했다. ignore/숨김 파일·외부 권리 관계까지 조사한 것이 아니며 저작권 부재나 자유 이식 허용을 뜻하지 않는다. 원본 코드 권리와 선별 dependency·font/icon/asset 라이선스·lockfile 고지는 실제 이식 전에 확인해야 한다.
4. `.env`·자격증명·실제 사용자 데이터·운영 DB/bucket은 읽거나 복사하지 않았다. 설정 **소스 정의**는 의존성 판단에만 참고했다. 현재 설치 패키지의 버전·서비스 계정 권한·유료 모델 동작은 미확인이다.
5. 실제 이식 시 초기 조사서의 기록 형식에 symbol·원본 커밋·대상 경로·삭제한 정책·새 dependency·라이선스·검증 결과를 기록한다. HEAD가 바뀌면 해당 파일 diff를 다시 확인한다.
