# R2 tombstone 정리 공정성 수정

2026-10-16 · Task `task_bc3553b66f67` · Dispatch `ctx_5baadaeba131`

## 원인

worker main은 매 poll에서 `scan_incomplete_uploads`를 기다린 후 `validation.run_once`를 호출했다. 삭제 페이지의 source/normalized/thumbnail 등 각 asset이 동일한 canonical 파생 키를 다시 HEAD하여, 이미 정리한 페이지도 반복 원격 지연을 만들었다. 스캔이 StorageUnavailable/timeout을 던지면 같은 try 블록 뒤의 검증 작업은 실행되지 않았다.

## 변경

- `backend/uploads/validation.py`: 한 `_scan_deleted_assets` 실행 안에서만 key별 존재/부재를 캐시한다. 각 원격 key는 최대 한 번 HEAD하며, 다음 scan에서는 캐시를 새로 만들어 late PUT을 다시 찾는다. 파일 확인 시 DB row lock을 잡지 않고, enqueue 직전 기존 소유권·tombstone 검증을 유지한다.
- `backend/worker/__main__.py`: 매 poll에서 validation/cleanup job을 먼저 처리한다. 작업, maintenance, storage sweep, generation의 예외 경계를 분리해 스캔 실패가 처리 가능한 작업을 차단하지 않는다.
- R2 sweep은 최대 10행의 단일 비동기 작업으로 실행한다. 진행 중인 스캔이 있으면 추가 스캔을 만들지 않으며, 성공/실패 완료 확인 후 30초를 기다린다. 따라서 느린 HEAD/SDK timeout을 기다리는 동안에도 다음 poll의 검증 작업이 진행된다. local은 기존 매 poll·100행 정책을 유지한다.
- 종료 시 진행 중인 스캔 coroutine을 취소하고 회수한다. 이미 시작한 동기 SDK 요청 스레드는 Python 취소로 중단되지 않지만, 한 key씩 await하므로 취소 후 추가 원격 요청을 이어서 실행하지 않는다. SDK timeout 경계는 기존 R2Storage 설정을 따른다.

## 검증

실제 PostgreSQL 17.11과 실제 R2Storage를 사용하고 외부 S3만 메모리 클라이언트로 대체했다. 신규 `backend/tests/integration/test_r2_sweep_fairness.py`는 같은 페이지의 3개 asset에 대해 canonical 6키의 HEAD 중복 제거, source 404 뒤 late result 발견, 정리 후 다음 scan의 새 late PUT 재발견·삭제를 검증한다. main 실제 루프에는 최소 worker stub을 주입하여 foreground 처리 순서, R2 주기/10행 제한, local 매 poll/100행 유지, StorageUnavailable/TimeoutError 이후 지속 처리를 확인한다.
