# 휴대전화 주이미지 정규화 수정 결과 — 2026-10-16

## 범위와 원인

총괄이 제공한 비식별 진단값을 바탕으로 수정했다. 작업자는 실제 사용자 사진, QA 사진 저장소, `.env`, 기존 `moriai`를 읽거나 복사하지 않았다. 실제 사진 변환 재검증과 QA 배포는 총괄 소유이며 이 보고서의 합성 테스트 성공과 구분한다.

- JPG: Pillow가 두 프레임 컨테이너를 `MPO`로 식별하여 기존 JPEG/PNG/WEBP/HEIF 목록에서 `UNSUPPORTED_MEDIA`로 거부했다.
- HEIC: 8비트 RGB 주이미지와 Display P3 ICC가 있었지만 보조 `hdrgainmap` 식별자까지 주이미지 HDR로 취급하여 거부했다. 제공된 RGB TRC는 ICC parametric function 3의 sRGB 곡선 계수였다.

## 변경 파일과 동작

- `backend/media/normalize.py`: MPO의 처음 열린 주 JPEG 프레임을 허용한다. 추가 프레임 seek/합성 없이 EXIF 방향 보정, LittleCms ICC→sRGB, WebP 정규화를 수행한다. HEIF는 기존 primary 선택을 유지하고 주이미지 HDR 신호와 보조 gain map 식별자를 분리한다.
- `backend/media/icc_sdr.py`: 보조 gain map이 있는 HEIF 주이미지의 SDR 근거를 검증한다. 최대 1 MiB, 선언된 profile 길이, RGB/acsp 헤더, XYZ 또는 Lab PCS, 태그 테이블·offset·size 범위/정렬/중복, 세 채널 TRC 존재 및 동일성을 확인한다. `para` function 3 또는 4만 허용하고 sRGB 계수와 오차 `2/65536` 이하를 요구한다. function 4의 추가 계수는 0이어야 한다. 단순 감마·linear curv·알 수 없는 TRC·프로필 이름만으로는 허용하지 않는다. 실제 색상 변환은 계속 LittleCms가 담당한다.
- `backend/tests/media/test_phone_primary.py`: 합성 MPO, 실제 HEIF 픽셀 encode/decode, auxiliary 메타데이터 주입, ICC 구조 및 transfer 경계 검증 33개를 추가했다.
- 이 문서: 검증 근거 및 한계.

새 외부 코드 이식 없음. 기존 프로젝트 정규화 경로를 수정했으며 의존성·Git·공통 계약 파일 변경 없음. 공개 DTO/API/오류코드 변경 없음; 허용 입력의 좁은 확장이므로 핵심 문서의 최종 정리는 총괄 담당이다.

## 허용 조건과 거부 유지

보조 HDR gain map이 있는 경우 **HEIF 주이미지가 명시적 8비트 RGB/RGBA이고, nclx transfer가 없음/unspecified(2)/sRGB(13)이며, 실제 ICC RGB TRC 세 채널이 검증된 sRGB 곡선**일 때만 주픽셀을 처리한다. 보조 이미지의 픽셀을 가져오거나 gain map을 적용하지 않는다. 주이미지 XMP gain-map 신호 및 실제 gain_map/HDR 메타데이터, 10/12/16비트, PQ/HLG, 미확인 transfer, 누락/잘못된 ICC는 이 예외로 통과하지 않는다.

이는 HDR 전체 지원이나 HDR tonemapping 구현이 아니다. 기존 일반 SDR 처리 경로의 허용 정책을 전면 재정의하지 않으며, 이 ICC 검증은 보조 HDR 때문에 거부되던 HEIF의 제한적 예외를 증명하는 역할이다. 원본 bytes는 불변이며 반환 sha256은 원본 전체 컨테이너 기준이다. 메타데이터 원문을 출력하는 로깅은 추가하지 않았다.

## RED → GREEN

기존 locked `mori-ai:verify-tests` 이미지, Linux amd64, network none, backend 읽기 전용 bind mount에서 실행했다.

RED:

```sh
docker run --rm --platform linux/amd64 --network none \
  -v "$PWD/backend:/app/backend:ro" -w /app mori-ai:verify-tests \
  python -m pytest backend/tests/media/test_phone_primary.py -q -p no:cacheprovider
```

수정 전 **3 failed, 15 passed**: MPO 테스트는 `UNSUPPORTED_MEDIA`, HEIF function 3/4 허용 테스트는 `IMAGE_NORMALIZATION_FAILED`로 의도한 거부를 재현했다. 수정 직후 동일 명령 **18 passed**.

최종 GREEN(추가 ICC 경계 테스트 포함):

```sh
docker run --rm --platform linux/amd64 --network none \
  -v "$PWD/backend:/app/backend:ro" \
  -v "$PWD/tests/fixtures/media:/app/tests/fixtures/media:ro" \
  -w /app mori-ai:verify-tests \
  python -m pytest backend/tests/media -q -p no:cacheprovider
```

**108 passed in 6.09s**. 기존 미디어 회귀 75개와 새 33개 모두 통과했다. 기존 gain-map XMP 거부 테스트와 충돌하지 않아 허용 경로 밖 테스트 수정이 필요하지 않았다.

검증에는 MPO 두 프레임 `save_all` 인코딩, 방향 보정 후 주프레임 픽셀 동일성, 원본 hash, 보조 프레임 seek 금지, `HeifImage.get_aux_image` 호출 시 실패하도록 한 가드, 원본 HEIF 픽셀의 실제 decode/ICC/WebP 처리, 주이미지 HDR 거부, 잘못된 프로필 길이·헤더·태그 offset/count·채널 불일치·미확인 곡선·허용 오차 초과 거부를 포함했다. 총괄이 전달한 실제 폰 TRC 계수도 합성 ICC에 넣어 통과했다.

HEIF encoder는 auxiliary 작성 기능을 제공하지 않으므로 테스트는 실제 8비트 HEIF 주이미지를 생성한 뒤 공개 `image.info`의 aux 정보만 주입했다(거부 테스트는 해당 주메타데이터도 주입). 실제 사용자 HEIC의 보조 컨테이너 구조나 Display P3 기준 색상 정확도를 이 mock으로 검증했다고 주장하지 않는다. 전체 backend/DB 테스트와 실제 사용자 보존 원본 재검증은 실행하지 않았으며 총괄 후속 범위다.

## 공식 문서 확인

- [Pillow MPO](https://pillow.readthedocs.io/en/stable/handbook/image-file-formats.html#mpo): 처음 열 때 주이미지를 선택하고 다른 프레임은 seek로 접근하며 save_all/append_images로 다중 프레임을 저장한다.
- [pillow-heif HeifImage](https://pillow-heif.readthedocs.io/en/stable/reference/HeifImage.html): bit_depth는 파일의 비트 깊이이며 aux는 유형별 이미지 ID 목록이다. 보조 이미지는 get_aux_image로 접근하고 현재 보조 이미지 쓰기는 지원하지 않는다.

## 총괄 실제 원본 확인 및 로컬 반영

2026-10-16 총괄이 기존 QA 원본을 읽기 전용으로 child-process watchdog 경로에서 재검증했다. JPG(MPO)는 방향 적용 후 2316×3088, 정규화 WebP 4,407,744 bytes; HEIC는 3024×4032, 7,246,498 bytes로 성공했다. 두 원본의 SHA256은 검증 전후 동일했다. 이미지·EXIF·파일명·서명 URL은 보고서에 포함하지 않았다.

기존 승인 OAuth runtime에 미디어 수정 두 파일만 반영한 `mori-ai:phone-fix`를 기존 로컬 QA web/worker에 적용했다. http://127.0.0.1:8000 의 기존 DB·사진·세션은 보존했다. 이미 rejected인 페이지는 자동으로 ready로 바꾸지 않으므로 실패 항목 삭제 후 다시 첨부한다. 당시 저장소 모드는 local이며 이 수정의 성공을 실제 R2 또는 실제 AI 성공으로 취급하지 않는다.
