## 1. 목적과 완료 기준

Orca에서 Codex 작업자들을 조율하여 사진첩 서비스를 개발한다. 기존 서비스의 필요한 기술을 선별 재사용하면서 공통계약에 맞게 독립 실행 가능한 새 서비스를 만든다. 현재 산출물은 개발 운영 방향이며 제품 기능을 구현하는 실행 계획은 아니다.

성공 기준은 다음과 같다.

1. 모든 작업에 담당자·편집 범위·선행 조건·검증·완료 기준이 있다.
2. 프론트엔드와 서버가 같은 DTO·상태·오류·샘플을 사용한다.
3. 공통 파일의 동시 편집과 운영 환경의 혼용을 방지한다.
4. 재사용 코드의 출처·의존성·수정·검증을 추적할 수 있다.
5. 완료 보고와 통합 검증으로 실제 동작을 확인하며, 외부 계정 미준비와 코드 결함을 구분한다.

기준 문서는 [AGENTS.md](../AGENTS.md), [공통계약](공통계약-v1.md) v1.3, [설계](설계.md), [재사용조사](재사용조사.md)다. 제품 기획과 DTO를 이 문서에서 다시 정의하지 않는다.

## 2. 운영 방식

**총괄 Codex 1개 + 동시 작업자 최대 2개로 시작**한다. frontend·backend·media·AI/worker·검토는 역할이며 모두를 상시 실행하는 것이 아니다. 작업 크기와 파일 충돌을 확인해 역할을 배정하고, 검토는 구현 결과가 준비된 뒤 수행한다. 동시 수 확대는 실제 독립 작업과 실행 자원이 확인된 뒤 결정한다.

| 방식 | 적합한 경우 | 이번 적용 |
|---|---|---|
| 독립 터미널에서 수동 병렬 작업 | 결과 교환이나 선후 관계가 없는 작은 작업 | 간단한 독립 조사에 한정 |
| Orca 감독형 Run·Task·Dispatch | 의존성·완료·질문·통합을 추적해야 하는 개발 | 기본 방식 |
| 별도 자체 오케스트레이션 프로그램 | Orca가 제공하지 않는 별도 제품 요구가 있는 경우 | 현재 만들지 않음 |

총괄은 작업 조율·계약·통합을 담당하고, 작업자는 배정된 결과물을 만든다. 총괄이 직접 코드를 수정하는 경우에도 해당 경로를 작업자가 동시에 편집하지 않도록 소유권을 확보한다.

## 3. 역할과 편집 소유권

아래 경로는 **향후 배치 제안**이다. 현재 제품 디렉터리가 존재하거나 구현된 것은 아니다. 개발 기반 작업에서 실제 경로를 확정한 뒤 각 Task에 좁은 파일 범위로 지정한다.

| 역할 | 책임 | 제안 편집 범위 | 공유 파일 처리 |
|---|---|---|---|
| 총괄·통합 | 분해·배정·계약·검토 수용·통합 | AGENTS.md, docs/, 공통 계약 정의, root 설정·CI·실행 스크립트 | 직접 소유하거나 한 Task에 명시적으로 위임 |
| 프론트엔드 | 책장·업로드·정렬·진행·검토·뷰어·BGM | frontend/의 배정 feature·테스트 | 공통 transport·인증·의존성은 별도 소유자 지정 |
| 백엔드 | 인증·동의·소유권·API·도메인·DB | backend/의 배정 API·domain·repository·테스트 | migration은 백엔드 소유자 1명만 작성 |
| 미디어 | 업로드·검증·HEIC·날짜·WebP·URL·정리 | backend/의 media·storage adapter·테스트 | DB·공통 port 변경은 총괄과 백엔드 조율 |
| AI·worker | provider adapter·task 실행·시도·복구·집계 | backend/의 generation·AI adapter·테스트 | claim·fence·outbox 저장 계약은 백엔드와 먼저 고정 |
| 검토 | 계약·테스트·실사용 흐름·재사용 범위 확인 | 기본 읽기 전용 | 수정은 별도 Task로 구현 소유자에게 배정 |

같은 backend 디렉터리의 작업이라고 모두 안전하게 병렬화할 수 있는 것은 아니다. 실제 파일 경계와 import 계약을 확인한다. 공통 DTO·enum·port, package manifest·lockfile, migration, Compose·환경설정·CI·bootstrap에는 동시에 한 편집자만 둔다.

## 4. 개발 단계와 합류점

| 단계 | 작업 | 병렬 조건 | 산출물·완료 조건 |
|---|---|---|---|
| A. 설계 정리 | 현재 핵심 문서 검토·역할·경계 정리 | 제품 구현 없음 | 개발 방향 확인, 미정 항목과 결정 담당 명시 |
| B. 재사용 확정 | 후보의 의존성·테스트·라이선스·원본 버전 조사 | frontend와 backend를 읽기 전용으로 병렬 조사 가능 | 재사용 조사서의 후보별 판정·대상 경로 확정 |
| C. 개발 기반 | 독립 프로젝트 골격·공통 타입·설정·로컬 runtime·검증 명령 | 공통 파일은 단일 소유자 | mock으로 실행 가능, 환경 격리 확인 |
| D. 기능 병렬 개발 | UI, API/DB/인증, media, AI/worker를 작은 Task로 구현 | 선행 port·편집 경계가 확정된 작업만 최대 2개 | 각 Task 검증과 계약 준수 |
| E. 통합·검토 | 실제 흐름 연동·회귀·실패 복구·수정 | 변경 중인 결과와 검토 기준을 혼용하지 않음 | 합류점별 검증, 발견 결함 수정 확인 |

의존 흐름은 `B → C → D → E`다. D 내부에서는 UI가 샘플 응답으로, 생성 엔진이 가짜 AI adapter로 진행할 수 있다. media가 정규화 입력을 제공하기 전에는 실제 AI 연동 성공으로 판정하지 않는다.

합류점은 공통계약 6절을 따른다.

1. 로그인 → 초안 → 검증된 업로드 → 생성 접수.
2. 실제 AI 처리 → 영속 결과 → review_ready.
3. 글귀 저장 → publish → viewer → 삭제.

독립 조사와 mock 개발을 외부 계정 준비 때문에 막지 않는다. 실제 OAuth·저장소·AI 호출은 새 서비스 계정과 예산·설정이 준비된 별도 통합 작업에서 수행한다.

## 5. 체크아웃과 환경 격리

- 문서 작성 시점 `mori_ai`는 초기 커밋이 없고 기존 문서·이미지·PDF는 untracked다. 실행 전에 포함 파일과 제외 파일을 검토하고 재현 가능한 기준 커밋을 준비한다. 현재 문서 작성 요청만으로 자동 commit·push하지 않는다.
- 같은 checkout에서는 서로 겹치지 않는 파일 작업 또는 읽기 전용 조사를 진행할 수 있다. Git index·branch·의존성·runtime 변경은 총괄이 직렬화한다.
- 공통 파일 동시 변경, 서로 다른 branch의 검증, 독립 DB/runtime이 필요한 작업은 파일·환경 충돌을 밝히고 Orca worktree로 격리한다.
- Orca 부모·자식 표시와 Git base는 별개다. 작업의 선행 변경이 들어간 정확한 기준 커밋에서 시작한다. 새 worktree에는 미커밋 문서가 자동 복사되지 않으므로 기준 문서의 존재를 확인한다.
- worktree별 포트, Compose project, DB, 저장소 경로·volume과 채택 시 Redis namespace을 분리한다. 실행 계정·설정은 `mori_ai`용으로 준비한다.
- setup hook은 기반 작업에서 정의한다. 현재 Orca 등록 정보에는 setup script가 없다. 새 worktree에서 `--setup run`을 지정하는 것만으로 의존성 설치가 준비되는 것은 아니다.

## 6. Orca 실행 계약

제품 구현은 현재 실행하지 않는다. 사용자가 승인한 문서 조사의 실행·결과는 [기술 결정 전 준비 작업](archive/2026-10-16/기술결정-전-준비작업.md)에 기록한다. 향후 구현을 실행할 총괄은 먼저 설치 버전의 가이드를 읽고 runtime 연결·오케스트레이션 기능·Codex 실행 가능 상태를 확인한다.

```bash
orca skills get orca-cli
orca skills get orchestration
orca status --json
```

정상 개발 루프는 다음과 같다.

1. 총괄의 실제 Orca agent terminal에서 Run을 생성하거나 바인딩한다.
2. Task에 목표·문서·범위·선행 작업·검증·완료 조건을 기록한다.
3. 선행 조건을 충족한 작업을 `worker-start`로 배정한다. 같은 checkout 또는 별도 worktree 배치를 명시한다.
4. 총괄은 질문·escalation·완료 메시지를 처리한다. 워커 질문은 ask/reply, 작업 진행을 결정하는 관문은 gate를 사용한다.
5. 작업자는 현재 Dispatch 지시에 따라 성공 또는 실패를 명시해 완료 보고하고 해당 작업을 끝낸다.
6. 총괄은 변경과 검증 결과를 확인하고, 작업자를 즉시 후속 Dispatch에 재사용하거나 `worker-release`로 해제한다. 이후 통합·검토 Task를 진행한다.

Run은 작업 묶음·우편함이며 자동 스케줄러가 아니다. Task 의존성이 있다고 작업자가 저절로 시작되거나 파일 충돌이 해결되지 않는다. 총괄이 배치·동시 수·준비 상태를 판단한다. 외부 셸에서 임의의 터미널을 발신자로 가장하지 않고 설치 가이드의 바인딩 규칙을 따른다.

오래된 `coordinator-start`, `run` scheduler 예제를 복사하지 않는다. Task/Dispatch가 실제 생성되었는지 조회한 뒤 오케스트레이션 실행으로 보고한다. 명령 응답이 유실되면 receipt·상태를 먼저 확인하고 중복 작업자를 바로 실행하지 않는다.

공유 checkout에서 commit SHA가 없으면 변경 파일·검증 대상 상태를 명확히 남긴다. 격리 branch에서는 기준·결과 커밋을 함께 보고한다. 완료 메시지에 테스트가 있다고 실제 실행한 것으로 간주하지 않는다.

## 8. 통합과 실패 처리

- 총괄이 통합 순서를 정하고 파일 충돌을 해결한다. 검토자는 기본 읽기 전용이며 수정은 명시적으로 재배정한다.
- 계약 변경이 필요하면 제안·영향 목록·타입/샘플 변경을 함께 준비한다. 영향 받는 구현은 이전 계약으로 계속 확장하지 않는다.
- 제품 범위·정책 변경, 새 외부 비용·운영 자원 사용, 이식 권한 불명확은 사용자 결정 항목이다. 계약 안의 일반적인 구현 선택·오류 수정은 총괄이 처리한다.
- 타임아웃은 실패 확정이 아니다. Task/Dispatch·worker 상태와 출력으로 진행 여부를 확인하고, 기존 작업자가 편집 중인 상태에서 같은 경로에 대체 작업자를 실행하지 않는다.
- 실패 Task의 후속 작업은 원인과 편집 상태를 확인해 재배정한다. 성공 부분을 보존하며 reset·clean으로 타 작업자의 변경을 제거하지 않는다.
- 모든 Task 완료 후에도 전체 서비스 완료를 주장하지 않는다. 공통계약의 통합 시나리오와 실제 사용자 흐름을 검증한다.

## 9. 구현 전 남은 결정

| 항목 | 결정 시점·담당 |
|---|---|
| 문서 방향과 최초 개발 범위 | 사용자 검토 후 총괄이 첫 개발 묶음 정의 |
| 후보별 최종 이식 여부·대상 파일 | B 단계 조사 담당 제안, 총괄 확정 |
| 코드 디렉터리·패키지·검증·setup 명령 | C 단계 총괄 및 기반 담당 |
| 실제 큐·배포 구성 | 개발 기반 설계 시 선택, 외부 자원은 사용자 범위 확인 |
| 글귀 provider/model·계정·예산·BGM | 실제 연동 전 사용자와 담당자 결정 |

현재 문서는 이 결정을 완료했다고 주장하지 않는다. 단계별로 필요한 항목만 확정하고 이미 공통계약에 결정된 제품 정책은 다시 열지 않는다.

## 10. 첫 구현 묶음

1. **기반 담당:** 새 manifest·lock·Docker/Compose·검증 entrypoint를 작성하고 V01 통과. frontend/API 공통 타입과 DB 경로의 단일 편집자 지정.
2. **병렬 묶음 1:** media 담당은 V02·V09, backend 담당은 V03·V04를 준비. frontend는 샘플 기반 화면을 진행할 수 있으나 오케스트레이션의 동시 작업자 수는 총괄이 조율.
3. **병렬 묶음 2:** 실제 storage·OAuth·AI 연결은 V06~V08로 나눔. 외부 준비가 없는 영역은 가짜 adapter로 개발하고 미연동으로 표시.
