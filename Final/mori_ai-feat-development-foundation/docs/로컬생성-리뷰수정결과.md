## I1 원인과 수정

기존 action_required의 AI claim 차단 및 failed-only resume는 각각 계약에 맞았다. 그러나 원래 unknown 결과를 회수해 succeeded로 바꾼 뒤에도 미발송 queued/retry_wait AI가 남으면, 완료 집계는 미완료로 반환하고 그 AI는 claim·resume 양쪽에서 제외됐다. 기존 강제 종료 테스트는 나머지 queued task를 미리 failed/safe_to_retry로 바꾸므로 순수 미발송 잔존 경로를 놓쳤다.

`classify_deferred_ai`를 기존 completion settlement의 Album→Run→전체 Task 잠금 transaction에 연결했다. 현재 album/run이 action_required·active_run이고 unknown이 하나도 없을 때만, queued/retry_wait AI task의 다음 근거를 확인한다.

- task에 보존 입력 표시가 있고 결과 참조/글귀가 아직 없다.
- 활성 page가 같은 album에 있으며 normalized가 snapshot ID/SHA와 일치하고 같은 owner/album/page의 ready WebP다.
- latest attempt가 없으면 attempt_count도 0이어야 한다.
- latest attempt가 있으면 현재 attempt_count와 번호가 일치하고 dispatch_state가 not_sent/rejected여야 한다. unknown/received 상태나 이미 보존 출력이 있는 attempt는 제외한다.

근거가 충족되면 task만 `failed + safe_to_retry + AI_TEMPORARY_FAILURE`로 분류한다. run/album은 action_required를 유지하고 새 AI는 자동 발송하지 않는다. 기존 명시 resume의 예산·동의·version·키 규칙을 그대로 사용한다. 분류 과정은 기존 attempt·attempt_count·fence·output·input/config snapshot을 변경하지 않는다. 기존 unknown recovery의 실행권 재확보 fence 규칙 자체는 바꾸지 않았다.

추가 경합도 확인했다. 원래 unknown 회수 당시 다른 task가 claim된 running이면 분류에서 제외해야 한다. 이후 그 task가 prepare 또는 mark_sent 직전에 action_required를 보고 미발송 queued로 되돌아오는 경우에도 같은 completion policy를 호출하여 실행 보류 failed로 노출한다. 두 경계의 기존 not_sent ledger와 fence/count를 그대로 보존한다. 실행 중 accepted task는 안전 미발송으로 바꾸지 않고 늦은 원래 결과를 정상 보존·settle한다.

현재 공개 enum/endpoint/DTO/schema는 변경하지 않았다. 총괄이 공통계약 3.2·샘플·승인 계획에 기존 failed-only 명시 resume의 실행 보류 해석을 추가했고 해당 문구를 확인했다. 이 작업자는 공통계약 문서를 편집하지 않았다.

## U1 조사와 harness 교정

첫 좁은 진단은 기존 fast lease 2초/heartbeat 0.1초 및 maintenance 없는 drain 그대로 **1 passed, 48.14초**였다. 따라서 원래 리뷰에서 발생한 50장 실패 자체를 이 실행에서 다시 관찰했다고 주장하지 않는다.

별도의 단일 페이지 통제 검사는 caption 결과를 실제로 보존한 뒤 receive 직전에 DB lease만 만료시켰다. 실제 `_received`는 attempt를 received로 보존하지만 현재 실행권이 없으므로 task를 연결하지 않는다. 기존 drain은 다음 실행 가능한 task가 없으면 종료하여 다음 상태로 실패했다.

```text
run_status=running
 task_counts={running:1,succeeded:2}
 caption task: fence=1, attempt_count=1, lease < now
 latest attempt: received, dispatch_state=accepted_or_unknown
 output_caption_present=true, stored_output=true
```

이 상태는 worker가 maintenance에서 원래 결과를 회수하도록 설계된 정상 복구 경계다. 제품 worker는 매 claim 앞에 maintenance를 실행하지만 기존 부하 harness는 그것을 생략했다. 따라서 **보존 결과의 만료 실행권을 회수하지 않는 harness 결함은 통제 검사로 원인을 확인했다**. 다만 원래 U1 실패 당시 task dump가 없으므로 그 실패에서 정확히 어느 경계가 만료됐는지는 소급 확정할 수 없다.

정상 완료/부하 검사는 실제 worker의 기본 90초 lease/15초 heartbeat 및 매 claim 전 maintenance를 사용하는 `drain_worker`로 바꿨다. 단순 timeout 증가로 처리하지 않았고 같은 통제 만료 입력에 대해 maintenance가 보존 결과를 연결하여 **succeeded·AI attempt 1회 유지**로 전환됨을 확인했다. 기존 `drain`, fast 2초 lease/0.1초 heartbeat 및 process kill·unknown·stale fence 장애 회귀는 그대로 유지했다. assert나 page/task 기대값, 151회 부하 실행 상한을 완화하지 않았다.
