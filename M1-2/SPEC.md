# 동화 열람 데이터 AI 비서 구현 명세

작성일: 2026-10-26

## 1. 목적과 범위

운영 중인 동화 서비스의 일별 열람 횟수를 관리하고, 통계 요약에 기반한 AI 답변을 제공한다.
이 문서는 프로젝트 루트의 과제 요구사항 PDF와 학습 대화에서 합의한 규칙을 구현 가능한 형태로 정리한다.
최초 명세 작성 당시에는 CSV 검증까지만 수행했다. 이후 사용자가 단계 0~4 구현과 실연동·배포 검증을 승인했다. 최신 실행 상태는 docs/stages-2-4-report.md를 따른다.

필수 기능:
- 데이터 기반 AI 채팅과 로딩 표시
- 일별 기록 추가·조회·수정·삭제 및 요약 표시
- 대화 자동 저장, 목록 조회, 불러오기, 삭제
- 프론트·백엔드 배포, Swagger UI, README와 제출 스크린샷

보너스 과제는 수행하지 않는다. 다음 항목은 구현·학습·완료 검증 범위에서 제외하며, 추후 구현 예정으로도 두지 않는다.
- Function Calling을 통한 AI 도구 호출
- MCP Server 또는 GPT Actions 연동과 관련 호출 흐름 문서화
- 보너스용 추가 통계 지표 및 별도 통계 API
- 그래프 시각화
- CSV/JSON 내보내기
- 다크 모드 토글

기본 요약 API의 합계·평균·최대·최소·최근 추세, 요약 화면 표시, CSV 초기 가져오기는 필수 기능을 위한 범위로 유지한다.
아래 문서 ID, 응답 형태, 중복 처리 등은 별도 사용자 합의가 없었던 부분을 구체화한 구현 기본안이다.

## 4. 데이터와 가져오기

### 일별 기록

Firestore `data` 컬렉션에서 날짜 문자열을 문서 ID로 사용한다.

| 필드 | 형식 | 규칙 |
| --- | --- | --- |
| date | `YYYY-MM-DD` 문자열 | 유효한 날짜, 날짜별 한 문서 |
| value | 정수 | 0 이상, 열람 횟수. 이용자 수가 아님 |
| memo | 문자열 | 특이사항. 생략 시 빈 문자열 |

API의 `id`는 문서 ID이며 `date`와 같다. JSON의 숫자 문자열·불리언·소수는 value로 허용하지 않는다.
중복 날짜 추가는 409로 거절한다. 수정에서는 value와 memo만 변경하며 날짜는 고정한다.
날짜 변경은 기존 기록 삭제 후 새 날짜 추가로 처리한다.

CSV는 초기 가져오기 자료이며, 이후 서비스의 기준 데이터는 Firestore다.
가져오기 전에 전체 행을 검증하고 오류가 있으면 쓰기를 시작하지 않는다.
기존 날짜는 건너뛰고 개수를 보고하며, 기존 값을 묵시적으로 덮어쓰지 않는다.
원본 CSV는 DB 변경과 자동 동기화하지 않는다.

### 누락 날짜

사용자 합의에 따라 최초~마지막 저장 날짜 사이의 누락 날짜는 실제 열람 0회로 계산한다.
요약을 만들 때 날짜를 보완하고, 가상의 0회 문서를 DB에 자동 생성하지 않는다.
관리 목록은 실제 저장된 문서를 보여준다.
중간 날짜를 삭제하면 그 날짜는 요약에서 0회가 된다. 최초·마지막 기록을 삭제하면 분석 범위도 달라진다.

### 대화

Firestore `conversations` 컬렉션에 대화별 자동 ID를 부여한다.
문서는 `title`, `created_at`, `updated_at`, `messages`를 가진다.
시각은 서버에서 생성하고 API에서는 UTC ISO 8601 문자열로 반환한다.
메시지는 `role`(user/assistant), `content`, `created_at`으로 구성한다.
제목은 첫 질문의 앞부분으로 생성한다. 대화 목록은 updated_at 내림차순으로 제공한다.

## 5. 요약 및 비교 규칙

### 확정 규칙

1. 기준일은 오늘이 아닌 저장 데이터의 마지막 날짜다.
2. 최초~마지막 날짜를 양 끝 포함하고 누락일을 0회로 채운다. 이 달력 날짜 수를 N으로 둔다.
3. N >= 14이면 최근 7일과 그 직전 7일을 비교한다.
4. 2 <= N < 14이면 k = floor(N / 2)로 정하고 최근 k일과 직전 k일을 비교한다.
5. 홀수 길이에서 남는 가장 오래된 하루는 비교에서만 제외하고 전체 통계에는 포함한다.
6. N < 2이면 비교 기간 부족이다.
7. 직전 평균이 양수이면 변화율 = (최근 평균 - 직전 평균) / 직전 평균 × 100이다.
8. 직전 평균이 0이면 변화율은 null이고 상황 설명을 별도 제공한다.

| 상황 | 비교 상태 | 설명 |
| --- | --- | --- |
| 데이터 없음 또는 1일 | insufficient_data | 비교 기간이 부족합니다. 최소 2일이 필요합니다. |
| 직전·최근 모두 0 | zero_baseline | 두 기간 모두 열람이 0회입니다. 변화율은 계산하지 않습니다. |
| 직전 0, 최근 양수 | zero_baseline | 직전 기간에는 열람이 없었고, 최근 기간에는 일평균 N회가 기록됐습니다. 기준값이 0이므로 변화율은 계산하지 않습니다. |
| 직전 양수 | comparable | 두 기간과 변화율을 명시 |

증가·감소·유지는 반올림 전 두 평균을 비교해 판단한다. 동일하면 유지다.
평균과 변화율은 화면에서 소수점 둘째 자리까지 표시하며, 중간 계산값은 반올림하지 않는다.

### 요약 응답 계약

| 필드 | 내용 |
| --- | --- |
| period | start, end. 데이터가 없으면 null |
| count | 실제 저장 문서 수 |
| calendar_days | 누락일 보완 후 전체 달력 일수 |
| filled_zero_days | 0회로 보완한 날짜 수 |
| metrics | total, daily_average, max, min |
| metrics.max / min | value와 동률을 포함한 dates 배열 |
| comparison | status, window_days, previous, recent, change_percent, trend, message |
| comparison.previous / recent | start, end, average. 비교 기간 부족이면 null |
| comparison.trend | increase / decrease / unchanged / insufficient_data |
| notable_memos | 빈 메모를 제외한 date, value, memo 목록 |

daily_average는 total / calendar_days이며, 최대·최소도 보완한 0회 날짜를 포함한다.
데이터가 없으면 count/calendar_days/filled_zero_days/total은 0, 평균·최대·최소는 null, 메모 목록은 빈 배열이다.
비교 기간 부족이면 window_days는 0, change_percent는 null이다.
화면과 AI 답변에는 실제 비교 날짜와 기간 길이를 표시한다.

## 6. API 계약

데이터 응답 Record: `{id, date, value, memo}`.
Conversation 상세: `{id, title, created_at, updated_at, messages}`.

| 메서드·경로 | 요청 | 성공 응답 |
| --- | --- | --- |
| POST /api/data | date, value, memo(선택) | 201, Record |
| GET /api/data | 없음 | 200, `{items: Record[]}`. 날짜 오름차순 |
| PUT /api/data/{id} | value, memo | 200, 수정된 Record |
| DELETE /api/data/{id} | 없음 | 204, 본문 없음 |
| GET /api/data/summary | 없음 | 200, 위 요약 객체 |
| POST /api/conversations | title, messages | 201, 새 Conversation 상세 |
| GET /api/conversations | 없음 | 200, `{items: [...]}`. messages 제외한 목록 |
| GET /api/conversations/{id} | 없음 | 200, Conversation 상세 |
| DELETE /api/conversations/{id} | 없음 | 204, 본문 없음 |
| POST /api/chat | message, conversation_id(선택) | 200, `{conversation_id, answer}` |

messages는 user/assistant 역할만 허용한다. 빈 질문이나 공백뿐인 질문은 거절한다.
주요 오류: 입력 오류 422, 존재하지 않는 ID 404, 중복 날짜 409, 외부 서비스 실패 502/503, 예기치 않은 오류 500.
프론트는 상태 코드와 detail을 처리한다. 내부 키·인증 정보는 오류에 포함하지 않는다.

## 7. 채팅 처리와 답변 원칙

1. 질문과 conversation_id를 검증한다. 기존 ID가 지정되면 해당 대화가 있어야 한다.
2. 최신 데이터 요약을 준비한다.
3. 서버가 관리하는 시스템 프롬프트에 요약과 답변 규칙을 삽입한다.
4. 기존 대화의 이전 메시지와 새 질문을 GPT에 전달한다.
5. 답변 생성 성공 후 질문·답변을 같은 대화에 저장한다. 새 대화이면 ID를 생성한다.
6. 저장 성공 후 conversation_id와 answer를 프론트로 반환한다.

채팅 자동 저장에는 프론트의 별도 POST /api/conversations 호출이 필요하지 않다.
수동 저장 API는 별도의 대화 생성 기능이며, 자동 저장과 중복 호출하지 않는다.
GPT 호출 실패 시 성공한 답변처럼 저장하지 않는다. 저장 실패 시 성공 응답을 보내지 않는다.
사용자 질문과 memo는 데이터로 다루며, 그 안의 지시가 시스템 규칙을 바꾸지 않도록 한다.

지원 질문: 전체 열람 규모, 일평균, 최대·최소 날짜, 최근 추세, 메모와 변동 시점의 관계.
요약에 없는 정보는 알 수 없다고 답한다. 열람 횟수를 이용자 수로 해석하지 않는다.
메모와 수치 변화의 동시 발생을 인과관계로 확정하지 않는다.
비교 불가·0 기준값을 설명하고 null을 0%로 바꿔 말하지 않는다.
데이터가 없으면 기록 추가를 안내하며 수치를 만들어내지 않는다.

## 8. 필수 화면

- 채팅: 메시지 입력, 질문·답변, 로딩, 오류·지연 안내, 새 대화 시작
- 요약: 기간, 실제 기록 수와 달력 일수, 주요 지표, 비교 기간·변화율·예외 문구
- 데이터 관리: 날짜·횟수·메모 추가, 날짜순 목록, 횟수·메모 수정, 삭제
- 대화 기록: 이전 대화 목록, 선택한 대화 불러오기·이어가기, 삭제
- 데이터 변경 성공 후 목록과 요약을 새로 조회한다. 실패를 성공으로 표시하지 않는다.
- 과제의 화면 최소 조건은 추가·조회와 수정/삭제 중 하나지만, 기본안은 수정·삭제 모두 제공한다.

## 9. 배포와 제출

- 백엔드 코드는 GitHub에 올리고 Render Web Service에 배포한다. `/docs` 접근을 확인한다.
- 프론트는 Vercel에 배포한다. 빌드/배포 시 공개 설정에 API_BASE_URL을 반영한다.
- 서버 환경 변수: OPENAI_API_KEY, FIREBASE_SERVICE_ACCOUNT_JSON(또는 키 경로), ALLOWED_ORIGINS.
- 모델명과 요청·출력 토큰 제한은 구현 단계에서 설정한다. 개발 중 호출 횟수를 제한한다.
- 비밀 키는 백엔드에만 두고 Git·브라우저·로그에 노출하지 않는다. CORS에는 허용 프론트 출처를 설정한다.
- 첫 요청 지연 안내를 제공한다.
- README: 서비스 소개, 기술 스택, 프론트/API/Swagger URL, 로컬 실행, 환경 변수 목록, CSV 가져오기 방법.
- 제출 화면: 요약과 질문·답변이 함께 보이는 채팅, CRUD 동작, 이전 대화 불러오기.

## 10. 구현 후 완료 확인

- CSV를 120개 날짜의 기록으로 가져오며 재실행 시 기존 기록을 덮어쓰지 않는다.
- CRUD가 DB와 화면에 반영되고, 음수·잘못된 날짜·중복 날짜를 적절히 거절한다.
- 빈 데이터, 1일, 2일, 5일, 13일, 14일 이상의 비교 구간이 규칙과 일치한다.
- 누락일은 0회, 홀수 기간의 남는 하루는 전체 통계에 포함된다.
- 직전 평균 0의 두 경우에 null과 상황별 문구가 표시된다.
- 데이터 변경 후 요약과 다음 AI 답변이 최신 기록을 사용한다.
- AI가 수치·비교 기간을 정확히 설명하고 이용자 수·인과관계·없는 정보는 단정하지 않는다.
- 대화가 자동 저장되고 새로고침 후 목록·전체 메시지 복원이 가능하다.
- 프론트와 백엔드 배포 URL, CORS, `/docs`, README와 제출 스크린샷을 확인한다.

위 항목은 완료 검증 기준이다. 항목별 최신 결과는 작업 보고서와 배포 체크리스트에 기록한다.
