# B1-3 노코드 자동화 미션 수행 계획

## 1. 과제 한눈에 보기

이 과제의 목적은 반복 업무를 노코드 자동화 워크플로우로 바꾸고, 도구별 차이와 도구 선택 근거를 설명하는 것이다.

완성해야 할 것은 다음 두 프로젝트다.

1. **프로젝트 1: 자동화 도구 비교 구현**
   - 동일한 워크플로우를 서로 다른 자동화 도구 2개 이상으로 각각 구현한다.
   - 각 구현의 설정 화면과 실행 결과를 증거로 남긴다.
   - 최소 5개 비교 기준을 사용해 도구별 장단점과 적합한 상황을 분석한다.
2. **프로젝트 2: 자유 주제 자동화 설계 및 구현**
   - 자동화할 반복 업무를 직접 하나 정한다.
   - 도구 하나를 선택하고 선택 이유를 설명한다.
   - 자동으로 실행되는 워크플로우를 설계하고 실제로 구현한다.

단순히 실행 성공 화면만 제출하는 과제가 아니다. 다음 내용을 이해하고 설명할 수 있어야 한다.

- Trigger: 워크플로우를 시작시키는 사건 또는 일정
- Action: Trigger 이후 수행되는 처리 동작
- Filter/Router: 입력값에 따라 서로 다른 경로로 보내는 조건 분기
- 실행 로그: 각 단계에 들어온 데이터와 처리 결과를 확인하는 기록
- 도구 선택 기준: 기능, 사용성, 비용, 연동 범위, 로그와 오류 처리 방식 등의 차이

## 2. 필수 요구사항 해석

### 2.1 모든 워크플로우에 적용할 기준

안전한 제출을 위해 프로젝트 1의 각 도구 구현과 프로젝트 2 구현 모두 아래 구조를 갖추는 것으로 계획한다.

- 실제로 동작하는 워크플로우
- Trigger 1개 이상
- Action 2개 이상
- Filter 또는 Router 1개 이상
- 조건의 참/거짓 또는 각 Router 경로를 최소 1회씩 실제 실행
- 각 실행을 로그와 결과 화면으로 증명

즉, 프로젝트 1에서 2개 도구를 쓰고 프로젝트 2에서 1개 흐름을 만들면 최소 3개의 작동하는 워크플로우 구현이 생긴다.

### 2.2 프로젝트 1에서 반드시 지킬 것

- 도구를 2개 이상 직접 사용한다.
- 두 도구에서 업무 목적, Trigger, 분기 기준, Action 구조를 같게 만든다.
- 단순히 비슷한 주제만 사용하는 것이 아니라 같은 입력 데이터와 같은 테스트 케이스를 사용한다.
- 비교 보고서에 다음 항목을 넣는다.
  - 사용한 도구 이름과 사용 환경
  - 구현 과정 요약
  - 비교 항목 5개 이상
  - 각 도구의 장점과 단점
  - 각 도구가 적합한 상황에 대한 의견

### 2.3 프로젝트 2에서 반드시 지킬 것

- 반복되는 실제 업무 하나를 정의한다.
- 선택한 도구와 선택 이유를 적는다.
- 수동 실행만 가능한 시연이 아니라 Trigger 발생 시 자동 실행되게 한다.
- Trigger부터 최종 결과까지의 흐름을 문장이나 다이어그램으로 설명한다.
- 구현 화면과 실행 결과 화면을 남긴다.

### 2.4 선택 사항

- 생성형 AI Action으로 요약, 분류 또는 메시지 초안을 자동 생성한다.
- 실패 알림, 재시도 또는 대체 저장 경로를 설계한다.

보너스를 수행하더라도 필수 흐름을 먼저 완성하고 증거를 확보한 뒤 추가한다.

## 3. 권장 구현 주제

계정 연동 차이 때문에 두 도구의 기능이 달라지는 문제를 줄이기 위해 프로젝트 1의 Trigger는 공통 Webhook을 사용하는 방식을 권장한다.

### 3.1 프로젝트 1: 문의 점수에 따른 자동 분류

**권장 도구 후보:** Make + n8n

- Make: 시각적 Router 구성과 실행 데이터 확인이 쉽다.
- n8n: 동일한 흐름을 노드 단위로 재현하기 좋고, 자체 호스팅 환경을 사용할 수 있다.
- 최종 선택 전 두 도구의 현재 무료 플랜, 필요한 연동, 실행 한도와 조건 분기 지원 여부를 공식 문서에서 다시 확인한다.

**업무 시나리오:** 외부 문의 데이터가 들어오면 관심 점수에 따라 우선 상담 대상과 일반 관리 대상으로 나누고, 각각 기록과 알림을 처리한다.

**공통 입력 예시:**

```json
{
  "name": "홍길동",
  "email": "hong@example.com",
  "score": 85,
  "message": "서비스 도입 상담을 원합니다."
}
```

**동일하게 구현할 흐름:**

```text
Webhook Trigger
    |
    v
score >= 80 ?
    | yes                         | no
    v                             v
Google Sheets의 우선상담 탭 기록   Google Sheets의 일반문의 탭 기록
    |                             |
    v                             v
Discord/Slack 우선 알림 전송        Discord/Slack 일반 알림 전송
```

각 분기에는 Action이 2개씩 있어 요구사항을 여유 있게 충족한다.

**필수 테스트 데이터:**

| 테스트 | score | 예상 분기 | 예상 결과 |
|---|---:|---|---|
| P1-T1 | 85 | 우선 상담 | 우선상담 탭 1행 추가 + 우선 알림 1건 |
| P1-T2 | 60 | 일반 문의 | 일반문의 탭 1행 추가 + 일반 알림 1건 |
| P1-T3 | 80 | 경계값 | `score >= 80` 규칙에 따라 우선 상담 처리 |

두 도구에 같은 JSON을 입력하고 결과 데이터가 같은지 비교한다.

### 3.2 프로젝트 2: 예약된 업무 요청의 우선순위별 자동 알림

**권장 도구:** 프로젝트 1에서 더 적합하다고 판단한 도구

**반복 업무:** Google Sheets에 쌓인 신규 업무 요청을 일정 간격으로 확인하고, 우선순위에 따라 담당 채널에 알림을 보낸 뒤 처리 상태를 자동 변경한다.

**자동 실행 흐름:**

```text
Schedule Trigger
    |
    v
Google Sheets에서 status=NEW 행 조회
    |
    v
priority=HIGH ?
    | yes                         | no
    v                             v
긴급 채널에 알림                   일반 채널에 알림
    |                             |
    v                             v
status=NOTIFIED로 행 업데이트       status=NOTIFIED로 행 업데이트
```

**도구 선정 이유에 포함할 내용:**

- 일정 Trigger를 설정하기 쉬운가
- Google Sheets와 메신저 연동이 안정적인가
- 분기 흐름과 실행 로그를 한 화면에서 확인하기 쉬운가
- 무료 실행 한도로 과제 테스트를 마칠 수 있는가
- 오류가 났을 때 실패한 단계를 찾기 쉬운가

**필수 테스트 데이터:**

| 테스트 | priority | 초기 status | 예상 결과 |
|---|---|---|---|
| P2-T1 | HIGH | NEW | 긴급 알림 + `NOTIFIED` 변경 |
| P2-T2 | NORMAL | NEW | 일반 알림 + `NOTIFIED` 변경 |
| P2-T3 | HIGH | NOTIFIED | 재처리하지 않음 |

P2-T1과 P2-T2는 각 분기의 실행 증거이고, P2-T3는 중복 알림 방지 검증이다.

## 4. 단계별 수행 계획

### 0단계: 작업 환경과 증거 저장 규칙 준비

1. 사용할 Google, Discord 또는 Slack 계정을 준비한다.
2. 계정 이메일과 채널명에 개인정보가 들어가는지 확인한다.
3. 결과 파일 이름과 폴더 구조를 먼저 정한다.
4. 스크린샷에 API Key, Webhook 전체 URL, 토큰, 비밀번호가 보이지 않게 한다.

권장 폴더 구조:

```text
B1-3/
├── docs/
│   ├── mission.md
│   ├── implementation-plan.md
│   ├── project1-comparison-report.md
│   └── project2-design-report.md
└── submit/
    ├── project1/
    │   ├── make/
    │   └── n8n/
    └── project2/
```

### 1단계: 프로젝트 1 공통 명세 확정

1. 입력 JSON 필드를 `name`, `email`, `score`, `message`로 고정한다.
2. 분기 기준을 `score >= 80`으로 고정한다.
3. 각 분기의 Sheet 탭과 알림 문구를 고정한다.
4. 테스트 케이스 P1-T1~P1-T3를 작성한다.
5. 두 도구의 결과를 비교할 때 사용할 성공 기준을 확정한다.

완료 기준: 도구에 상관없이 동일하게 구현할 한 장짜리 흐름 명세가 있다.

### 2단계: 프로젝트 1의 첫 번째 도구 구현

1. Webhook Trigger를 만든다.
2. 테스트 JSON을 보내 입력 필드가 잡히는지 확인한다.
3. Router 또는 IF 노드로 `score >= 80` 분기를 만든다.
4. 우선 상담 분기의 Sheet 기록과 메신저 알림을 연결한다.
5. 일반 문의 분기의 Sheet 기록과 메신저 알림을 연결한다.
6. P1-T1~P1-T3를 실행한다.
7. 전체 구성, 각 분기 실행 로그, Sheet 결과, 알림 결과를 캡처한다.

완료 기준: 세 테스트가 예상대로 통과하고 두 경로의 실행 증거가 있다.

### 3단계: 프로젝트 1의 두 번째 도구 구현

2단계와 같은 입력, 분기 기준, Action, 테스트를 사용한다. 도구 특성 때문에 노드 이름이 달라도 논리 구조와 최종 결과는 같아야 한다.

완료 기준: 첫 번째 도구와 같은 세 테스트가 통과하고 대응되는 화면 증거가 있다.

### 4단계: 프로젝트 1 비교 보고서 작성

최소 다음 8개 기준으로 비교한다.

1. 워크플로우 UI와 흐름 가독성
2. 최초 설정 난이도
3. 조건 분기 표현 방식
4. 연동 서비스와 인증 편의성
5. 데이터 매핑과 변환 편의성
6. 실행 로그와 디버깅 기능
7. 오류 처리와 재실행 방식
8. 현재 무료 플랜 범위와 예상 과금 방식

가격과 무료 한도는 변할 수 있으므로 보고서 작성일에 각 도구의 공식 가격 문서를 확인하고 조회일과 출처 링크를 적는다. 비교 결론은 “무조건 어느 도구가 좋다”가 아니라 업무 규모와 사용자의 기술 수준에 따라 적합한 상황을 나눠 쓴다.

### 5단계: 프로젝트 2 문제 정의와 설계

1. 누가 어떤 반복 업무를 하는지 한 문장으로 정의한다.
2. 현재 수작업의 빈도, 소요 시간, 실수 가능성을 적는다.
3. 입력 데이터와 최종 결과를 정한다.
4. 도구 선정 기준을 프로젝트 1 결과에 연결한다.
5. Trigger, 조회 Action, 분기, 알림 Action, 상태 변경 Action을 다이어그램으로 그린다.
6. P2-T1~P2-T3의 예상 결과를 적는다.

완료 기준: 구현 전에 입력, 분기, 출력, 성공 기준이 문서로 고정돼 있다.

### 6단계: 프로젝트 2 구현과 자동 실행 검증

1. Schedule Trigger를 활성화한다.
2. `status=NEW`인 행만 조회하도록 설정한다.
3. `priority=HIGH` 조건으로 두 경로를 만든다.
4. 각 경로에 알림과 상태 업데이트 Action을 연결한다.
5. 수동 테스트로 데이터 매핑 오류를 먼저 제거한다.
6. 워크플로우를 활성화하고 예약된 Trigger가 실제로 발생할 때까지 기다린다.
7. 자동 실행 시간과 로그를 캡처한다.
8. P2-T1~P2-T3 결과를 확인한다.

완료 기준: 수동 Run 버튼이 아니라 예약 Trigger가 만든 성공 로그가 있고, 두 분기 결과와 중복 방지 결과가 확인된다.

### 7단계: 보너스 추가

필수 기능이 모두 통과한 뒤 하나만 선택해도 충분하다.

- AI Action: 문의 또는 업무 요청을 한 문장으로 요약해 알림에 포함
- 실패 대응: Sheet 기록 실패 시 별도 오류 시트에 원본 데이터 저장 후 관리자 채널에 알림

AI Action을 쓸 때는 개인정보를 외부 모델에 보내도 되는지 확인하고, API Key와 프롬프트 속 개인정보가 캡처되지 않게 한다.

### 8단계: 최종 검수와 제출 패키징

1. 요구사항 체크리스트를 한 항목씩 확인한다.
2. 모든 이미지에서 키, 토큰, Webhook URL, 비밀번호, 이메일을 마스킹한다.
3. 스크린샷 번호와 보고서의 그림 번호를 일치시킨다.
4. 공유 링크를 제출한다면 비로그인 또는 평가자 권한으로 열리는지 확인한다.
5. 깨진 링크와 누락 이미지를 확인한다.
6. 최종 제출 폴더만 열어도 프로젝트 1과 프로젝트 2를 구분할 수 있게 정리한다.

### 5.3 제출 전 있으면 좋은 보조 자료

- 테스트 케이스와 Pass/Fail 표
- 실제 실행 가능한 워크플로우 공유 링크 또는 내보내기 파일
- 사용한 도구의 공식 무료 플랜/가격 출처 링크와 조회일
- 보너스 기능의 설계 및 실행 증거

공유 링크나 내보내기 파일은 원문에서 명시한 핵심 필수 산출물은 아니지만, 평가자가 실제 구현을 확인하기 쉽게 해준다.

## 7. 스크린샷 체크리스트

각 캡처에는 가능한 한 다음 정보가 보이게 한다.

- 워크플로우 또는 시나리오 이름
- 도구 이름
- Trigger, 조건, Action 노드 이름
- 조건식의 핵심 부분
- 실행 성공 상태와 실행 시각
- 분기에 사용한 입력값
- 각 노드의 성공 표시
- Google Sheets에 추가 또는 변경된 행
- Discord/Slack에 도착한 메시지

다음 정보는 반드시 가리거나 화면에서 제외한다.

- API Key와 Access Token
- Webhook 전체 URL
- 비밀번호
- 개인 이메일 전체 주소
- 실사용자의 이름, 전화번호, 문의 내용

테스트 데이터는 가상 이름과 예시 이메일을 사용한다.

## 8. 최종 합격 체크리스트

### 프로젝트 1

- [ ] 서로 다른 도구 2개 이상을 직접 사용했다.
- [ ] 두 도구의 워크플로우가 동일한 입력, 조건, Action 구조를 가진다.
- [ ] 각 도구 구현에 Trigger가 1개 이상 있다.
- [ ] 각 도구 구현에 Action이 2개 이상 있다.
- [ ] 각 도구 구현에 Filter 또는 Router가 1개 이상 있다.
- [ ] 각 도구에서 모든 분기를 최소 1회 실행했다.
- [ ] 구성 화면과 실행 결과 화면을 저장했다.
- [ ] 비교 기준을 5개 이상 사용했다.
- [ ] 각 도구의 장단점과 적합한 상황을 설명했다.

### 프로젝트 2

- [ ] 반복 업무 하나를 구체적으로 정의했다.
- [ ] 도구 하나를 선정하고 근거를 적었다.
- [ ] Trigger가 자동으로 발생하는 구조다.
- [ ] Action이 2개 이상 있다.
- [ ] Filter 또는 Router가 1개 이상 있다.
- [ ] 모든 분기를 최소 1회 실행했다.
- [ ] 워크플로우 흐름을 문장 또는 다이어그램으로 설명했다.
- [ ] 구현 화면과 자동 실행 결과 화면을 저장했다.

### 보안과 비용

- [ ] 키, 토큰, 비밀번호, Webhook URL이 노출되지 않는다.
- [ ] 이메일 등 계정 정보가 마스킹돼 있다.
- [ ] 무료 플랜을 우선 사용했다.
- [ ] 유료 기능을 썼다면 필요 이유와 무료 대안을 적었다.

## 9. 예상 위험과 대응

| 위험 | 영향 | 대응 |
|---|---|---|
| 도구의 무료 플랜에서 분기나 다단계 Action 제한 | 계획한 흐름 구현 불가 | 구현 시작 전에 공식 가격표와 기능표 확인, n8n 자체 호스팅 등 대안 준비 |
| Google 또는 메신저 인증 실패 | Action 테스트 불가 | Webhook과 테스트용 계정을 먼저 연결하고 최소 흐름부터 확인 |
| 자동 Schedule 실행 증거 누락 | 프로젝트 2 자동 실행 요구 증명 부족 | 제출 하루 전 활성화하고 실행 시각이 보이는 로그 캡처 |
| 한쪽 분기만 실행 | 공통 기능 요구 미충족 | 경계값을 포함한 분기별 테스트 데이터 사전 준비 |
| 같은 구조가 도구별로 달라짐 | 프로젝트 1의 비교 공정성 저하 | 공통 명세를 먼저 고정하고 도구 특화 기능은 비교 후 보너스로 분리 |
| 화면에 비밀값 노출 | 보안 제약 위반 | 테스트 계정 사용, 캡처 직후 확대 검수와 마스킹 수행 |
| 무료 실행 한도 소진 | 최종 검증 불가 | 작은 테스트 데이터 사용, 필수 테스트 완료 후 보너스 진행 |

## 10. 권장 작업 순서 요약

```text
공통 명세 작성
→ 도구 A 구현·테스트·캡처
→ 도구 B 동일 구현·테스트·캡처
→ 비교 보고서 작성
→ 프로젝트 2 문제 정의·설계
→ 자동 Trigger 구현·테스트·캡처
→ 선택 보너스
→ 보안 검수와 제출 패키징
```

가장 중요한 원칙은 구현 직후 바로 증거를 저장하는 것이다. 마지막에 한꺼번에 캡처하려 하면 실행 이력이 사라지거나 무료 한도가 부족해질 수 있다.
